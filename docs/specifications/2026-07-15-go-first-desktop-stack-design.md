# Go-first 桌面技术方案设计

- 日期：2026-07-15
- 状态：已批准

## 目标

在保持商业桌面产品质量要求的前提下，优先使用开发者熟悉的 Go，提高个人项目的交付速度、可维护性和持续迭代概率；同时保留对 Rust 的受控扩展能力。

## 方案比较

### 方案 A：Go + Wails v2，Rust 按需 Sidecar

Go 承担桌面后端和全部核心业务，Wails v2 连接 React 前端。只有 Go 缺少合适实现或有经过测量的性能问题时才引入 Rust Sidecar。这是批准方案。

优势是单一主语言、并发模型简单、开发速度快、现有 React 原型可复用，并能隔离可选 Rust 组件。代价是自动更新、系统凭据和部分商业基础设施需要在 Go/Wails 生态中单独设计。

### 方案 B：Tauri 2 + Go Sidecar

Tauri 负责桌面壳与官方插件，Go 作为主要业务 Sidecar。它保留 Tauri 的权限和升级生态，但从第一天就需要 Rust、Go、前端三套构建与进程通信，增加个人项目复杂度，因此不选。

### 方案 C：Rust + Tauri 2

技术一致性和安全边界较强，但开发者对 Rust 不熟悉，会降低迭代速度并提高长期维护成本，因此由 ADR-0002 取代。

## 模块设计

- Wails 层：窗口、生命周期、菜单、绑定和平台事件。
- Go 领域层：故事实体、约束和状态转换，不依赖 Wails、SQLite 或模型 SDK。
- Go 应用层：创作、续写、分析、审稿、修订、版本和导出用例。
- Go 基础设施层：SQLite、文件、模型供应商、凭据、升级和日志适配器。
- Go 智能体运行时：任务图、流式输出、暂停恢复、预算、重试、证据与仲裁。
- React 前端：作者交互和可视化，只使用类型化应用接口。
- Rust Sidecar：可选、独立发布单元，通过版本化协议被 Go 调用。

## 错误与恢复

Go 错误按领域、输入、供应商、网络、配额、平台和内部错误分类。Context 贯穿可取消操作；长任务在执行前持久化状态，崩溃后可以恢复。Sidecar 必须有超时、健康检查、协议版本和崩溃隔离，不能成为未记录的隐式依赖。

## 测试

- Go 领域和应用模块使用单元测试。
- SQLite 迁移、备份恢复和 Provider Adapter 使用集成与契约测试。
- React 使用组件测试，关键作者流程使用 Playwright。
- Rust Sidecar 同时通过 Cargo 测试和 Go 端协议契约测试。
- Windows 与 macOS 分别验证构建、安装、升级、凭据和文件系统行为。

## 实施约束

首个实施计划不得包含 Rust。只有 Go/Wails 基线稳定后，出现符合 ADR-0002 的明确需求时，才为单个 Rust Sidecar 单独设计、评审和实施。
