1. 系统拓扑

这条链路是产品主循环：界面发命令，应用层冻结任务并给出权威投影，再分三路做上下文装配、工作流编译调度、领域读写；真正的模型调用发生在内核四阶段之内；结果只进未确认候选区。作者确认后才写入 Canonical Head，并异步进入五层长期记忆；下次生成由 Assembler 按 Manifest 读回，模型不能自己翻整本书。

橙色虚线框表示架构已定义、默认章节工作流尚未挂上的专业分析节点。灰色框是本地确定性组件。青色为长期记忆：只在定稿后写入，经 Manifest 再进入下一次调用。

界面 应用编排 装配 / 路由 / 存储 模型节点 确定性组件 候选隔离 长期记忆

2. 设计原则（决定模块怎么切）

作者主权与候选隔离

模型输出永远不是事实。任何 AI 结果先进入候选 / Artifact / ChangeSet。只有作者确认后，短事务才写入 canonical 正文或正式资产。R3 连确认写入都不做，只证明能规划、能写、能审、能改。

能力 ≠ 模型槽 ≠ 界面步骤

节点用稳定 capability 说明为什么存在；用 R2.1 三个槽 planner / writer / continuity_reviewer 取模型；界面只看 public_stage_id。内部节点拆分不得迫使 React 改代码。

规划 / 写作 / 审阅隔离

写手不读审阅标准答案或其他模型隐藏推理。独立审阅互不读取结论。修订只拿规范化问题清单。复核者不能由修订槽兼任。

冻结后只读

创建运行时冻结工作流、Prompt、Schema、装配器、连接、模型、参数、预算、输入摘要和 Manifest。恢复与重试只读冻结值；重试产生新 attempt，旧记录保留。

3. 分层与包边界

依赖只允许向下。领域层不引用 Wails、React 或具体 Provider。Wails 保持薄绑定。React 不直连 SQLite、文件系统或模型。

层包职责
界面apps/desktop/frontend、prototype/驾驶舱、正文、审阅、档案、Lab。原型是视觉权威；未实现能力显示「尚未就绪」。
绑定apps/desktop（api.go / app.go）DTO 转换、目录选择、JobEvent 唤醒。不实现领域规则。
应用workspace、agentkernel、appsettings、appshell、creativeharness、ports用例、投影、编译执行、设置、Harness。消费者定义小接口。
领域agent、project、revision、world、story、timeline、canon、importing、extraction不变量、状态机、工作流 DAG、Finding、ChangeSet。
适配persistence/sqlite、agentassets、quality、providers、platform/*项目库、内嵌资产、lint、模型协议、凭据与文件锁。

4. UI 与绑定怎么设计

生产前端

固定一级导航对应路由：创作驾驶舱 Cockpit、正文与章节 Chapters、审阅与候选 Review、导入 Import、作品档案 archive/*、版本与交付 Versions。R3 额外保留 Lab 作为运行观察、对照和人工评分入口，不把内部节点 ID 暴露成作者必须理解的步骤。

Go 应用层提供权威投影（RunProjection / JobPublicProjection 等）。React 只把 public_stage_id 译成作者语言，例如上下文装配、章节导演、正文写作、独立审阅、有界修订、候选就绪。面板宽度、字号、专注模式属于本机视图状态，不进入作品事实，也不进入 Manifest。

Wails 边界

DesktopAPI 把前端调用转给 workspace.Service、appsettings.Service、appshell.Service、creativeharness.Service。长任务异步返回：内核提交 JobEvent 后，job_notifier.go 发轻量通知，客户端按 cursor 补拉。漏推、重复、乱序和 Bridge 重挂载由事件协议处理，收起运行面板不得取消后台任务。

5. 应用编排层怎么设计

workspace.Service — 作品生命周期与写屏障

它持有活动项目、跨进程 OS 锁、storeGeneration 和 JobLease。切换或关闭项目时先阻止新作业、取消或等待现有 lease，避免后台任务向已关闭 store 回写。可编辑模式才允许写；只读打开走恢复副本或只读 store。

具体智能体执行逐步委托给 agentkernel.Service，避免继续膨胀单个 agent.go。工作台投影、章节保存、ChangeSet 确认、导入抽取仍由 workspace 用例完成，因为它们是作品事实，不是模型编排。

agentkernel.Service — 冻结、执行、恢复

  • CreateRun：Compile 解析工作流 / Prompt / Schema / 装配器，校验哈希，生成与注册顺序无关的 CompiledWorkflow，原子写入 RunBundle。
  • Execute：按 DAG 拓扑执行；条件不满足（如 on_quality_issue 为假）不调用 Provider，记零用量完成并标 condition_not_met。
  • 格式非法允许一次 format_repair，独立预算，禁止借修复改语义。
  • 恢复创建新 attempt，已完成节点不重跑；canonical head 变化则拒绝。

其它应用服务

服务设计要点
appsettings应用级 settings.db：连接元数据、不可变 CreativeProfileVersion。API Key 不进库，只进 OS 凭据库。项目锁定精确方案版本。
appshell不含正文的最近项目索引、标题栏、关闭协议。路径失效只能提示重定位，不得在原路径建空项目。
creativeharness独立 Harness 库。固定原创种子对照单次直出 / 智能体初稿 / 修订稿。CI 用 Fake/Recorded Provider。
ports在消费方定义最小接口：ProjectStore、ModelProvider、WorkflowRegistry、CredentialStore、Clock。

6. 上下文装配怎么设计

选择权属于版本化 Assembler，模型不得自由遍历作品或把未确认建议升为事实。每个实际调用的节点生成独立 ContextManifest：来源类型、ID、版本、哈希、优先级、纳入/省略原因、是否 provisional、字符与估算 Token 预算。

装配顺序固定：硬约束与禁止项 → 当前任务与作者指令 → 已确认结构化输入 → 当前章节或必要近期正文 → 上游节点结果 → 软目标。预算不足按优先级截断；硬约束截不断则创建失败。

R3 来源限于 Harness 规格、作者指令、当前章节 revision、已明确选择的结构化资产、上游工件和锚点。每个纳入来源带 source_id@source_version 边界标记，计入哈希；节点输出里的引用只能复制这些公开标识。

代码落点：作品侧清单在 workspace/context_manifest.go（context-v2）；内核节点用 json.assembler v1 把 $task / $context / node:… 选择器渲染进 Prompt。二者都是确定性的，不让模型决定「读什么」。R7 之后 Assembler 的候选集来自五层长期记忆（结构化关系、时间线、活跃伏笔、近期窗口和本地检索），而不是把整本小说塞进上下文。详见 第 13 节。

7. 智能体内核怎么设计

内核不是「固定三个 Agent」，而是版本化 DAG 执行器。工作流定义含节点、边、入口、结果节点、预算策略、质量策略和定义哈希。一经用于运行不可改；任何 Prompt / Schema / 条件变化都发新版本。

统一任务信封

每个节点收到不可变 TaskEnvelope：任务类型、能力、工作流版本、canonical head、输入引用与 digest、Manifest ID、execution_binding（槽、连接、模型、参数）、prompt_binding / schema_binding（含 SHA-256）、预算与取消令牌。信封不含 API Key。

输出必须解码到强类型 Go 结构并 Validate()。自由文本不能决定领域状态。JSON 传输允许忽略未知字段噪声，领域校验仍拒绝缺字段、空值和非法枚举。

四阶段（对应你画的内核）

A. 章节导演

chapter_planner 把路线图和冻结上下文变成可执行叙事任务：章节目标、场景（视角、欲望、阻力、信息释放、状态变化）、硬/软锚点、禁止提前揭示、结尾钩子、允许即兴范围。每项区分 canonical 来源与本章创作建议。导演不写正文。

A′. 专业状态分析

需要时输出短小 ConstraintNote：连续性、人物动机与知识边界、伏笔与叙事债务、世界规则。不生成可拼接正文。领域类型已在 output.go；默认 quality.chapter.director 尚未插入这些节点，避免未经验证的成本。

B. 主写

默认一个 prose_writer 完成整章，保证声音统一。只读任务、上下文和导演产物。实验变体 slot-parallel 把写作拆成骨架 + 五类槽位 + 确定性拼接 + 整合缝合；槽位写手互不可见，整合不得新增情节事实。产品界面仍只看到「正文写作」。

C / D. 审阅与修订

最小工作流用综合 review_bundle 一次输出三类 Finding。拆分工作流变成 continuity / content / style 三节点，读同一正文后由 MergeFindings 合并。有 major/blocker 才触发一次有界修订；v2 再加独立复核。

10. 审阅发现、Merger 与门禁

ReviewFinding

统一结构：类别、严重度（blocker / major / minor / note）、状态、来源（模型审阅 / 确定性 lint / 作者）、Unicode rune 范围或约束引用、引文、建议动作。没有正文范围时必须引用约束，不能伪造引文。

Finding Merger

agentdomain.MergeFindings 只做规范化、精确重复合并、稳定排序、证据关联和同证据冲突标记。不调用模型，不补写问题，不降低严重度，不把「多数审阅者同意」当成覆盖 canonical 的投票。拆分审阅工作流在修订前必须经过它；内核 mergeReviewContents 对输入顺序幂等。

确定性 lint 与质量状态

quality.Engine 按冻结策略版本跑本地规则：空正文、字数偏离、代码围栏、提示词泄漏、硬锚点/禁止项、重复句段、机械排比、总结腔、测试集保留专名、修订丢失已满足硬约束、slot-parallel 的槽位覆盖与整合漂移。规则有 ID 和版本，阈值变化必须升质量策略版本。

质量状态与运行终态分离：工作流可以 completed 同时质量 blocked。任一未解决 blocker → blocked；无 blocker 但有 major 或审阅不完整 → needs_review；blocker/major 已解决且门禁通过 → passed。模型打分不能覆盖确定性 blocker。

修订复核

确定性对账只能证明改动能精确应用到原文，不能证明语义问题被解决。v2 的 revision_verify 读原问题、修订前后正文和改动明细，但剥离修订自述的 status/note。只有修订与复核都判 resolved 才退出未解决计数；复核登记的回归进入独立 ID 空间。

11. 领域模型与持久化怎么设计

作品与正文

Project / Chapter 是身份与顺序。ChapterRevision 不可变。CanonicalHead 指向作者当前确认版本。作者编辑、AI 改写、导入替换都产生新 revision，不覆盖历史。

资产

人物、势力、地点、规则、关系、时间线、事实、物品、知识边界、伏笔、大纲与场景卡分属 world / story / timeline。路线图目标形态是「全书 → 卷 → 故事弧 → 近期章节」；R4 才把策划候选映射为正式资产。

候选与变更

ChangeSet 承载未确认补丁（替换正文、更新/创建资产），带证据和指纹。应用或拒绝走短事务。Agent Artifact 另有谱系：基线、工作流、Manifest、digest，供差异、撤销和恢复引用。

运行痕迹

AgentRun + Steps + Artifacts + Findings + Manifest。JobEvent 是单调事件源，JobSnapshot 是可恢复投影。模型调用不在数据库事务中运行；落库是调用结束后的短事务。

项目包 .zjproject 含项目数据库（WAL、外键、Goose 迁移，禁止 GORM 自动迁移）、附件、导入原文、分支、快照。应用数据目录另存 settings 与最近项目。同步盘 / 网络盘有持续健康检查，不能只靠启动探针。

12. 候选区之后发生什么

拓扑最底层的 Candidate Buffer 是整条链路的安全阀：

  • R3：结果进入 Harness 工件或未确认候选。失败、取消、重试都不改 canonical。
  • R4：作品方案候选经作者确认后写入正式档案；对话修改先变成待确认 Action。
  • R5：单章作者审阅、编辑、定稿；定稿事务原子提交 revision、审阅摘要与版本信息。定稿成功不依赖后验模型。
  • R6：批次由多个独立 ChapterRun 组成；同批前序候选仅 provisional；检查点熔断进 needs_confirmation。
  • R7：后验工作流从 canonical revision 抽事实/状态/摘要/伏笔候选，校验后幂等写入五层长期记忆。未确认候选不能启动正式记忆写入。

五类产品工作流族共享同一 Kernel：story.foundation、story.roadmap、chapter.production、batch.production、chapter.posthoc。工作流族是用途标识，不是固定节点图。

13. 长期记忆怎么设计

人物、世界观、事实和伏笔首先是 AI 的可审阅长期记忆，其次才是作者控制面板。它不是把整本书反复塞进 Prompt，也不是作者必须先填满的资料库。最高事实来源永远是作者定稿的 ChapterRevision；摘要、状态和抽取结果都是可重建的派生物，必须能指回章节、revision 与正文证据。

工作流族 chapter.posthoc 与 chapter.production 共用 Agent Kernel，不另起运行时。观察与裁决拆成两个职责，避免抽取模型既找差异又给自己放行。

五层各装什么

层内容当前领域落点装配优先级
宪法层已确认作品方案、世界规则、主线、不可违背设定、禁写项、作者锁定world.WorldRule、方案资产、锚点中的硬约束最高；预算不足也不得截断。装不下则任务创建失败。
结构层全书 → 卷 → 故事弧 → 近期 3–10 章路线图story.OutlineNode / 路线图资产。默认只滚动近期层，高层变化要作者批准或 retcon硬结构稳定，近期层随批次刷新。
状态层人物、关系、物品、地点、能力、知识边界、未解问题world.*、canon.CharacterKnowledge（known 与 misinformed 分离）按本章出场、关系图和时间窗口筛选。
摘要层章节、卷、近期场景摘要R7 后验产物。近场用较细摘要，远场只保留骨架原文始终可回溯；摘要不能替代定稿正文。
证据层原文片段、revision、审阅发现、伏笔登记canon.Fact + Evidence、timeline.StoryEvent、world.ForeshadowingHook、ReviewFinding必须带章节 / revision / 引文范围。无证据不能自动变正式事实。

事实、状态与有效区间

canon.Fact 区分来源（作者 / 正文 / 模型 / 规则）和状态（作者确认 / 正文证据 / AI 推断 / 冲突 / 拒绝）。模型推断不得直接变成 author_confirmed 或 text_evidenced。事实可挂 validFrom / validUntil 事件，所以「曾经为真、现在已变」不会被当成连续性错误。人物知识边界单独建模：角色知道什么、被误导相信什么，不能把全书事实等同于角色所知。

伏笔是状态层与证据层的交叉：ForeshadowingHook 记录埋设章、到期章、已解决/已放弃。未回收钩子进入后续 Manifest；已解决或放弃的不得再当硬约束。叙事债务（承诺未兑现）由后验裁决节点从「未登记事件」归类，不能由写作模型自行注销。

chapter.posthoc 工作流

这是独立工作流族，不是写作流水线的尾巴。R5 只留定稿后异步挂点和 memory_pending_rebuild；完整节点在 R7 落地。

  • 唯一合法来源：作者定稿的 ChapterRevision。初稿、自动修订、未确认候选只能形成 provisional 状态，不能启动正式写入。
  • 观察节点：逐条比对定稿正文与现有记忆，只输出差异，不做「该不该入库」的判断。
  • 裁决节点：只读差异报告，不重读正文；把事实候选裁为采纳、待定或冲突；把未登记事件归为伏笔或叙事债务。
  • 应用层做证据、有效区间和一致性校验后，才幂等提交。模型调用不在数据库事务里跑；记忆失败不能阻止正文已经完成的定稿。
  • 定稿事务本身只提交 canonical revision、已有确定性校验、审阅摘要和版本信息，不夹带未完成的后验结果。

Manifest 与 Invocation Artifact

每次调用保存一份可解释的 ContextManifest：来源 ID/版本、范围、顺序、权重、选择原因、装配器版本、作者指令引用、预算、省略原因、用量和装配内容哈希。它不重复保存所引用的完整正文。完整 Prompt、请求体和流式事件是可选的 Invocation Artifact，可压缩、内容寻址和按保留策略清理；清理后仍必须能凭不可变来源、范围、模板版本和哈希解释当时上下文。项目瘦身不得删除 canonical 正文、候选、作者指令、必要证据或 Manifest 长期索引。

R3 已落地 Manifest 骨架和来源种类：harness_spec、author_instruction、chapter_revision、story_asset、upstream_artifact、anchor。完整检索（SQLite FTS5、结构化索引、可选本地向量，不依赖外部向量库）属于 R7。

批次中的 provisional

R6 的 GenerationBatch 由独立 ChapterRun 组成，每章自己的 Manifest。同批前序候选可以 provisional 身份进入后序上下文，让批次读起来连贯，但它们不是正式事实，检查点熔断或回退后不得写入长期记忆。回退只把后续候选标 superseded，不删证据、不改 canonical。

高层设定变更

影响分析先给范围、证据、风险和费用，作者确认后才能动未定稿内容；历史定稿默认只报告冲突。

模式含义
future_only只影响指定边界之后的内容，不改已发生事实。
in_story_change故事内事件导致状态变化，旧事实保留有效区间。
retcon追溯修改既有事实，必须显式批准，模型不得以「适配新正文」为由静默重写高层结构。

作者能看见什么

正文侧栏解释本章实际用到的规则、人物状态、时间地点、知识边界、锚点、活跃伏笔、叙事债务和被省略上下文，来源必须回到 Manifest 或 canonical 证据。作品档案页（大纲、人物、世界、时间线、伏笔）是同一套记忆的可编辑投影，不是第二份资料库。导入整书档案（R8）走独立抽取任务，产出跨章证据的候选包，确认后才并入这五层，不能把章节切片直接当成全书记忆。
