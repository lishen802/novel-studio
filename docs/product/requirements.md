# 织境 Story Studio 产品需求文档

- 状态：当前唯一权威需求文档
- 适用版本：首个可商业交付的 Windows/macOS 桌面版本
- 相关文档：[产品设计与技术架构](architecture.md)、[开发路线图](roadmap.md)

## 1. 产品定义

织境 Story Studio 是面向中文长篇网络小说作者的本地优先 AI 主创作桌面软件。它帮助作者从一句创意、已有设定、参考材料或已写小说开始，由 AI 主动完成构思、作品方案、章节路线图、正文候选、自动审阅和长篇连续性维护；作者始终拥有方向选择、直接编辑、确认定稿、回滚和导出的最终权利。

产品不是传统写作编辑器旁附加一个聊天框，也不是要求作者先手工维护资料库的辅助工具。大纲、人物、世界观、关系、时间线、事实与伏笔的首要角色，是 AI 长篇创作的可审阅长期记忆和作者控制面板。

## 2. 目标用户与核心价值

### 2.1 目标用户

- 想将模糊灵感发展为完整网文的个人作者；
- 已有设定或部分正文，希望让 AI 共同规划和连续创作的作者；
- 已写小说需要提取人物、世界观、大纲后继续写作的作者；
- 需要在多种模型之间选择写作与审阅能力，并希望作品资料留在本机的进阶作者。

### 2.2 核心价值

1. 降低从灵感到第一批可审阅正文的门槛；
2. 让 AI 主动规划和写作，而不是只做单段改写；
3. 让数十万到百万字作品保持人物、事实、时间线和伏笔连续；
4. 让作者在任何阶段能看见、干预、接受或否决 AI 的工作；
5. 支持不同模型承担规划、写作和审阅，避免单模型自洽偏差；
6. 在本地项目包中保存正文、版本、候选、证据和恢复资料。

### 2.3 首版商业与模型成本边界

- 首版采用用户自备模型能力（BYOK/BYOS）：作者使用自己的 API Key 或符合发布门槛的官方本地订阅运行时，软件不代购、转售或共享模型额度。
- 软件授权、试用和定价由独立商业方案定义；无论采用买断或订阅，均不得改变作者对本地项目包的访问、备份、恢复和导出权利。
- 模型调用成本不包含在软件授权价格中。任务启动前显示来源、预算与可能费用，任务结束后显示实际用量；无法估算时必须明确说明。

## 3. 产品原则

- AI 主创作：AI 默认承担方案与正文生成，作者不是表单录入员。
- 能力验证优先：核心智能体必须先通过可重复的创作质量 Harness 证明能规划、能写、能审、能改，再将对应能力扩展为完整上层业务界面。
- 作者主权：AI 不能静默覆盖正式正文、锁定设定或历史定稿。
- 定稿为依据：作者定稿的正文和确认资产是后续创作的 canonical 依据；正文中的人物陈述、传闻、猜测和不可靠叙述不能直接等同于世界客观事实。
- 候选隔离：AI 输出、导入抽取和修改方案先作为候选存在，确认后才进入正式数据。
- 长篇可追溯：记忆、事实和审阅结论必须可追溯到章节、revision 与正文证据。
- 本地优先：正文、项目状态和核心资产默认保存在作者电脑，不需要云端账户。
- 费用透明：模型来源、订阅/API、预算、失败和回退必须可见；不得静默产生额外 API 费用。
- 原创保护：参考材料只能用于高层类型与叙事特征分析，不能用于照抄角色、专名、情节链或文字表达。

## 4. 作品生命周期

```text
创建/导入作品
→ 创意或导入分析
→ 三套故事方向
→ 完整《作品方案》
→ 作者确认
→ 全书章节路线图
→ 有界批次创作
→ 自动审阅
→ 作者审阅、修改与定稿
→ 记忆更新
→ 下一批，直到完结/导出
```

每个阶段都可以回看、编辑和提出 AI 修改意见；任何会影响正式内容的操作都必须显示候选、差异、影响范围或确认动作。

## 5. 功能需求

### 5.1 作品与本地项目包

1. 作者可创建、打开、复制、导出和恢复小说项目。
2. 每部作品是作者选择位置下的 `.zjproject` 目录包，包含项目数据库、附件、导入档案、导出、分支和快照。
3. 项目可包含卷、章节、场景、正文 revision、恢复草稿、结构化资产、候选、运行记录和记忆。
4. 应用必须检测缺失、权限不足、损坏、未来 Schema、磁盘不足和并发占用，且不得用空数据库覆盖原项目。
5. 作者可以建立命名快照、章节版本和剧情分支，并从安全恢复点恢复。
6. 项目必须支持安全瘦身：清理或压缩可再生成的模型调用工件、临时流事件和过期缓存，但不得删除 canonical 正文、候选/revision、作者指令、正式资产、必要证据或 Context Manifest 的长期索引。瘦身前必须展示预计释放空间并建立可恢复操作记录。
7. 同一项目在可编辑模式下必须持有跨进程项目生命周期锁。锁被其他应用实例持有时，不得并发写入；界面应提供重试、只读打开或创建恢复副本等安全路径，并显示占用来源和可理解的处理建议。
8. 项目位于同步盘、网络映射目录或可能干预 SQLite WAL/原子替换的文件系统时，应用必须给出风险提示并持续处理运行期文件锁、只读、空间不足和共享冲突；不能仅依赖启动时的一次探针宣称项目安全。
9. 应用维护不含正文的最近项目索引，至少保存项目 ID、显示标题、路径引用和最后打开时间。最近项目可从首页直接打开；路径失效时只能提示重新定位或移除记录，不能在原路径创建空项目。
10. macOS 使用原生应用菜单，Windows 提供功能等价的窗口菜单。应用名称菜单只包含关于、应用设置、更新、隐藏和退出等应用操作；新建、导入、打开、最近项目、关闭、项目设置、导出和项目维护属于“文件”菜单。

### 5.2 从创意开始原创创作

1. 新建作品默认进入 AI 创作驾驶舱，不要求先填写大纲、人物或世界观表单。
2. 作者可输入一句创意、题材、情绪目标、已有设定、目标篇幅或任意自然语言要求。
3. AI 必须生成三套明显不同且原创的故事方向。每套至少包含卖点、目标读者/类型、主角、核心冲突、成长代价、主要节奏和结局方向。
4. 作者可选择、比较、要求重做、组合方向、直接编辑，或通过对话给出反馈。
5. 选择方向后，AI 生成完整《作品方案》，包括：

   - 故事定位与创作规格；
   - 主线、支线、关键冲突与结局方向；
   - 主角、主要人物、人物关系与人物弧；
   - 世界观、规则、地点、势力、物品；
   - 全书结构、卷/故事弧、节奏和预计章节；
   - 禁写项、作者锁定设定和风险提醒。

6. 作者可逐项查看、直接编辑、锁定、接受、拒绝或要求 AI 修改作品方案。
7. 只有作者确认后，作品方案中的资产才写入正式故事档案。
8. 原创作品使用连续的引导式构建工作台，至少覆盖“灵感与创作意图 → 故事方向 → 作品方案 → 人物与世界 → 全书路线图 → 确认作品档案”；顶部显示阶段、完成度、阻断原因和可恢复状态，内部 Agent 数量不得直接成为作者必须理解的步骤。
9. 工作台同时支持“分步审阅”和“自动推进”。分步审阅在每个阶段生成候选后暂停；自动推进仍必须在写入正式资产、改变锁定内容、产生无法预估费用或遇到阻断冲突前请求作者确认。
10. 每个阶段以结构化候选为中心，提供分类/实体导航、原地编辑、字段锁定、重新生成、版本比较和“确认并进入下一步”；重新生成只能产生新候选版本，不能直接覆盖作者正在审阅的版本。
11. 工作台提供绑定当前作品、阶段、实体、字段和所选候选的 AI 共创对话。对话可以分析缺口、提出问题、比较方向和解释影响，但不能绕过应用用例直接修改档案。
12. 对话中的修改建议必须转成结构化 Action Proposal，至少显示操作类型、目标资产/字段、基准版本、保持不变项、潜在下游影响、预计费用、参数摘要与确认/拒绝动作；作者确认后才执行。
13. 作者对上游阶段进行修改后，系统必须标出受到影响的后续候选、路线图和资产，并允许局部重算、保留为例外、继续讨论或放弃修改；不得静默级联重生成。
14. 新建作品不要求作者先填满固定的世界观或人物字段。字段和深度由题材、方向、已确认方案和后续写作需要决定；界面不得以字段数量替代故事质量或完成度。
15. 作者可在任何阶段退出并在重启后恢复到同一候选、阶段和审阅位置；恢复不能自动继续产生未重新确认的付费调用。

### 5.3 全书路线图与故事档案

1. 作者确认作品方案后，AI 生成全书章节路线图，至少覆盖卷、故事弧、章节范围、目标、转折、伏笔与预计节奏。
2. 路线图可逐层展开；第一版无需一次生成每章完整细纲。
3. 作者可直接调整顺序、目标篇幅、关键事件与结局，也可通过对话提出整体修改意见。
4. 大纲、人物、世界观、关系、时间线、事实、知识边界、物品与伏笔具有专门查看/编辑页面。
5. 每类资产均支持“作者直接编辑”和“AI 提出结构化候选”两种方式。
6. 作者锁定的规则和设定属于 AI 的硬约束；修改必须显式请求解锁或创建冲突候选。
7. 作者可在路线图节点或具体章节范围设置创作锚点（Anchor）：

   - 硬锚点：必须发生的事件、结果、信息揭示或不可改变的关键动作；
   - 软锚点：期望的情绪、节奏、氛围或表达方向；
   - 禁止项：不得出现的事件、行为、设定突破或表达。

8. 锚点必须进入相关模型调用的 Context Manifest；生成后审阅结果必须逐项显示满足、偏离或未覆盖状态。AI 不得将软锚点误报为硬约束，也不得静默忽略硬锚点。
9. 作品档案页继续支持绑定当前资产或字段的 AI 对话。任何 AI 修改先形成带基准版本、差异和影响范围的资产候选；作者直接编辑和 AI 修改都必须保留来源与版本。
10. 已确认资产发生变化时，下游候选使用明确的 `stale`/影响待处理状态；界面必须区分“可能受影响”和“必须修复”，不得把影响分析结果自动执行为重写。
11. 路线图采用“全书 → 卷 → 故事弧 → 近期章节”四层结构。全书层保存命题、终局、主角弧和不可破坏设定；卷层保存阶段目标、核心冲突和阶段回报；故事弧层保存事件因果、人物变化和伏笔；近期层提供未来 3–10 章的可执行目标。
12. 每批完成后默认只滚动刷新近期章节路线图。卷、故事弧或全书层的已确认内容只有作者批准相应影响方案或 `retcon` 后才能改变，模型不得以“适配新正文”为由静默重写高层结构。
13. 故事弧必须表达读者期待、阶段回报、人物不可逆变化、待兑现承诺、继续保留的悬念及对全书终局的推进；这些是待实现的规划目标，不能被当作已经发生的正文事实。普通事件和生活细节不必成为伏笔或必须回收的叙事债务。

### 5.4 有界批次正文创作

1. 作者在 `AI 写作` 中通过自然语言、章节选择或轻量控制卡开始创作。
2. 一次批次可生成 1–50 章，默认推荐 3–10 章；超过 10 章属于高级范围，必须额外展示级联偏离、耗时和费用风险。作者可设置本批目标字数、预算、创作指令与锚点。
3. 启动前必须展示章节范围、模型来源、预算/额度摘要、自动审阅范围、检查点间隔与熔断条件。
4. 批次按章节顺序执行：任务与预算预检 → 初步上下文装配 → 章节导演、按需状态分析与有界补查 → 冻结写作输入 → 单一主写模型生成正文 → 独立审阅与确定性 Finding Merger → 按需证据核验 → 有界修订 → 最终版本复检与候选选择 → 候选持久化。过程工件和各版候选持续保存，失败不能丢失前一版。
5. 同批后序章节可参考同批前序候选，但这些信息必须标记为 provisional，不能成为正式长期记忆。
6. 作者可以暂停、继续、取消、重试和在应用重启后恢复批次。
7. 同一作品分支同时仅允许一个非终态创作批次。
8. 当前批次中所有章节必须定稿、替换或明确废弃后，才能开始下一批。
9. 系统默认每 3–5 章执行一次跨章检查点，检查主线偏离、硬约束、人物状态、世界规则、时间线和未解决严重审阅项；作者可在 1–10 章范围内调整间隔。
10. 检查点发现硬锚点失败、锁定设定冲突、连续性严重矛盾、预算不足或重复修订仍无法通过时，批次必须进入 `needs_confirmation` 并停止后续模型调用。作者可修改候选、调整后继续、明确忽略风险或终止批次。
11. 熔断后必须提供以下非破坏性救局路径：

   - 修正并继续：修改触发问题的候选并重新审阅；
   - 回退生成进度：选择上一个检查点或批次中的某一未定稿章节作为重启点；
   - 接受风险继续：保留未解决问题并显式确认；
   - 结束批次：停止后续生成并保留已有候选。

12. “回退生成进度”不得修改 canonical 正文或物理删除候选。回退点之后的候选和审阅结果必须标记为 `superseded`，保留证据、费用和审计记录；系统在作者修改候选、路线图或锚点后重新构造 Context Manifest，并创建新的生成 attempt。若选定位置已经定稿，必须转入历史修订影响分析。
13. 执行回退前必须展示受影响候选、保留内容、是否涉及定稿、重新调用范围、预计费用和生成时的 canonical head；canonical head 已变化时必须重新分析。
14. 正文生产过程使用稳定的作者可见阶段投影，例如上下文装配、章节导演、角色/世界状态检查、正文写作、独立审阅、有界修订和候选就绪。界面不得直接依赖可随工作流版本变化的内部节点 ID。
15. 长任务运行窗口可收起，作者可继续阅读和编辑其他安全区域；完成后必须保留明确的“查看候选”入口，不得强制跳转或把生成结果自动写入正文。
16. `GenerationBatch` 必须由独立的 `ChapterRun` 组成，而不是一次覆盖多章的超长模型会话。每章分别保存 Context Manifest、attempt、用量、候选和恢复点；批次负责顺序、依赖、检查点、熔断和 provisional 状态传递。
17. 修改批次中较早章节后，只将实际依赖它的后续候选标为 `stale`。恢复应从最早受影响的未定稿 ChapterRun 开始，不得无条件从批次第一章重跑，也不得影响历史 canonical 正文。
18. 章节导演必须说明本章起始状态、关键选择与代价、结束状态及章节作用；按需体现情节推进、人物变化或读者认知变化，不要求所有维度填满。明确硬约束、可调整建议和即兴范围；正文新增的重要设定先作为候选，不能自动升级为正式事实或高层硬约束。
19. 导演、状态分析与审阅发现关键证据不足时，可以提出结构化补查请求。应用层控制作品/分支、章节范围、返回量、次数和总预算，记录来源及未查到事项；每次补查生成新的不可变上下文版本。模型不得自由遍历项目，未查到不能被解释为事实不存在，也不能用猜测填补硬约束。超过授权或仍缺关键证据时暂停、调整候选计划或交作者决定。
20. 创作检查分为章节、批次和故事弧三个尺度。每批检查跨章衔接、重复冲突、节奏和近期推进；故事弧结束时评估阶段回报、人物变化、承诺兑现和终局推进，提出下一阶段规划候选。评估必须标明基于定稿还是 provisional 内容，只有作者处理完本批并确认规划候选后才能用于下一批；高层变化仍遵循影响分析，不每章重规划全书。

### 5.5 自动审阅与作者定稿

1. 每个候选章节至少经过连续性、人物动机/知识边界、因果、节奏、世界规则和伏笔审阅。
2. 审阅角色应可使用不同供应商或不同模型，且彼此不读取对方结论。
3. 拆分审阅时，各审阅者必须读取同一正文、原始约束和冻结 Context Manifest。确定性 Finding Merger 只能去重、归类、关联证据和标出互相冲突的结论，不能凭空增加问题或静默降低严重度。
4. 作者在批次审阅队列中可逐章阅读、查看审阅摘要、直接编辑、要求重写、废弃或定稿。
5. 定稿前可以生成不进入正式记忆的事实预检候选；正文定稿事务只原子提交 canonical revision、已有确定性校验结果、审阅摘要和版本信息。正式 `chapter.posthoc` 在定稿后读取该 revision，再把验证通过的记忆候选独立提交。模型调用不得运行在数据库事务中；记忆提取失败不能阻止正文安全定稿，系统应标记为 `memory_pending_rebuild` 并在后续重建。
6. AI 不能将候选稿直接替换正式正文；作者直接编辑的正文同样必须成为新的 revision。
7. 正文工作台采用“卷/章节导航 + 中央正文编辑器 + 可收起的上下文/候选侧栏”。普通编辑时 AI 默认不遮挡正文；作者可通过选中文本、快捷键或侧栏显式唤起。
8. 中央编辑器必须提供自动保存状态、当前 revision、字数、查找、撤销/重做、版本入口、专注模式和本地排版偏好。排版和面板宽度属于本机视图偏好，不得改变正文内容或项目事实。
9. 选中文本后可请求解释、审阅、润色或按自然语言改写。请求必须绑定基准 revision、Unicode rune 范围和选中文本哈希；正文已变化时旧候选必须失效，不能按模糊字符串替换。
10. 局部改写返回独立候选和前后差异，支持全部接受、按差异项接受、放弃和撤销已应用修改。接受操作创建新的 `ChapterRevision` 或未定稿 revision，不直接修改历史版本。
11. 章节侧栏至少可解释本章实际使用的作品规则、人物状态、时间地点、知识边界、锚点、活跃伏笔、叙事债务、上游路线图和被省略上下文；来源必须能够回到 Context Manifest 或 canonical 证据。
12. 定稿正文应先安全提交；后验记忆提取、连续性回归或摘要生成可以异步完成。后验失败不得锁住正文编辑，但下一章 AI 生成前必须预检 `memory_pending_rebuild`、说明风险并提供恢复路径。
13. 审阅必须区分有证据的硬冲突、语义不确定问题和创作偏好建议。Finding Merger 不承担真伪裁决；按需核验可以补查并输出成立、不成立或证据不足，保留原始发现与理由。模型意见数量或严重度标签不能单独证明硬冲突；人物谎言、误解和有意留白不得未经核验就作为漏洞自动修复。
14. 修订请求必须绑定目标问题、基准候选、允许范围和保持项；每次修订后，包括文风修订和部分采纳后，都须检查目标是否解决及是否引入新问题。先执行确定性检查，再按影响范围复检语义；范围无法可靠确定时扩大复检。结论绑定具体正文版本、约束和上下文版本，旧版通过不能作为新版通过的证据。
15. 系统不得默认最后一版优于前一版。修订退化时可以选择仍符合当前约束且验证有效的前一候选；没有可用候选、争议未解或修订/费用达到上限时停止自动修订并交作者处理。候选比较需显示依据、未解决项及核验覆盖范围，不能以平均质量分掩盖新增硬冲突。
16. 文风修订遵循作者表达目标，不能将通用“去 AI 味”偏好强制当作硬规则。项目可保存明确确认的文风约定、作者自有样章引用和接受/拒绝的修改偏好；这些作为创作偏好进入运行冻结，不作为故事事实，未经确认不从单次编辑自动归纳永久偏好。

### 5.6 修改意见与影响分析

1. 作者可针对选中文本、单章、多章、作品方案或整批提交自然语言修改意见。
2. AI 默认先生成影响方案，而不是立即重写。
3. 影响方案至少说明：受影响候选、无需修改项、与定稿事实的冲突、计划变更、预计模型用量和生成时的 canonical head。
4. 作者确认后，系统仅重写受影响的未定稿候选；旧候选保留为可追溯版本。
5. 若作者在确认前修改或定稿相关内容，旧影响方案失效，必须重新分析。
6. 对长篇作品，默认只调整后续未定稿内容；历史定稿只有作者明确选择时才创建历史修订候选。
7. 作者解锁并修改作品方案、世界规则、主线、人物核心能力或其他硬约束时，必须先声明变更意图：

   - `future_only`：仅从指定章节或事件之后生效；
   - `in_story_change`：由故事内事件导致规则或状态发生变化；
   - `retcon`：追溯修正既有 canonical 设定。

8. 高层硬约束变更必须生成全局影响方案，覆盖历史定稿冲突、确认资产、未定稿候选、后续路线图、锚点、伏笔、人物弧、待执行批次和依赖旧规则的派生记忆。历史定稿只报告冲突和证据，不得静默修改。
9. 对未定稿内容，影响方案必须列出“需要解决”的项目及可选动作，包括重写、调整路线图、保留为有解释的例外、废弃候选或创建剧情分支；系统不得把“受影响”等同于强制重写。
10. 全局分析必须显示扫描范围、未检查区域、证据和预计费用。系统应先通过结构化引用、事实、时间线和摘要建立候选集，再按需读取原文和调用模型，不得默认将全部历史正文发送给模型。
11. `retcon` 或跨多卷的高影响变更在执行前必须创建一致性恢复快照，并建议建立剧情分支。影响方案绑定生成时的 canonical head；相关内容变化后立即失效。
12. 作品级 AI 对话可以提出读操作、写操作或付费操作；写操作和付费操作必须成为可持久化的待确认 Action，并绑定作品、会话、目标资源、基准版本、参数哈希和幂等键。
13. 待确认 Action 必须支持确认、拒绝、过期、冲突、执行中、成功、失败和结果未知状态。结果未知时先查询或恢复原操作，不能以再次点击的方式无条件重复执行。
14. 当存在未处理 Action 时，同一会话暂停继续发送可能改变目标状态的消息，直至作者确认、拒绝或恢复该 Action；只读解释不应被无关的写操作状态永久阻断。
15. AI 对话和字段/选区改写使用相同的作者主权规则：模型只生成建议或候选，应用层负责版本检查、费用授权、幂等、事务提交和审计。

### 5.7 百万字连续性与长期记忆

1. 系统必须支持连续创作数十万字，并为百万字级作品保留可扩展架构。
2. 原始定稿正文是最高正文证据来源，摘要不能替代原文；证据中的陈述含义可以待定、存在歧义或被后续揭示修正，不能把所有叙述句直接当作客观事实。
3. 系统自动维护作品硬约束、人物/物品/关系当前状态、卷/故事弧状态、章节摘要、事件、事实、伏笔和未解决冲突。
4. 每项 AI 派生记忆必须带来源章节、revision 与正文证据；验证失败的记忆不能自动变成正式事实。
5. 上下文装配必须使用结构化关联、时间线、伏笔、近期章节与全文检索，而不是把整本小说塞进模型上下文。
6. 每次模型调用必须保存可解释的 Context Manifest。Manifest 长期保存轻量、结构化的装配记录，包括引用章节/revision、记忆、锚点和路线图节点的 ID 与版本，引用范围、顺序、权重、选择原因，模板/装配器版本，作者指令引用，模型参数，Token/字符分配、遗漏原因、用量、耗时、Provider request ID 和最终装配内容哈希。Manifest 不要求重复保存所引用的完整正文。
7. 系统可从定稿正文重新提取派生记忆；重建不能改变正文和作者决策。
8. 完整 Prompt、Provider 请求体、流式事件和调试输出属于可选的 Invocation Artifact，不等同于 Context Manifest。它们应采用压缩、内容寻址与去重存储，并受可配置的回溯保留策略管理；超出保留范围后可降级为 Manifest、不可变来源引用和哈希。
9. 对已经产生 canonical revision 的调用，即使完整 Invocation Artifact 被压缩或清理，仍必须能依据不可变来源、引用范围、模板/装配器版本和哈希解释并校验当时的上下文组成。压缩或清理不得影响正文、候选 revision、作者指令和必要证据。
10. `chapter.posthoc` 只能以作者定稿的 ChapterRevision 为来源，依次产生事实、人物/物品/关系状态、摘要、伏笔和叙事债务候选，并经过证据校验后才进入正式长期记忆；初稿、自动修订稿和未确认候选不得触发正式记忆更新。
11. 状态候选必须记录生效章节/revision、有效时间或区间和正文证据。后续 revision 改变相关事实时，旧后验结果立即过期并重新抽取；抽取必须幂等，且失败不修改已定稿正文。
12. 后验提取先产生带语境的陈述与状态变化候选，区分客观事件、人物陈述、传闻、猜测、梦境和不可靠叙述；记录陈述者、相信者、知情者、故事内时间及叙述揭示位置。内容类型与采纳/待定/冲突状态分开：可以采纳“某人说过此话”，但不能据此采纳“此话属实”。
13. 观察与裁决是职责边界，不强制拆成两个模型调用。裁决默认读取带证据的差异报告，歧义时可请求应用层补读有界原文；证据不足保持待定，冲突单独保留，不覆盖已确认规则。只有经验证的解释进入正式记忆；重建保留作者裁定并检查其适用版本。
14. 普通事件、潜在线索、已建立的叙事承诺分别管理。未登记事件不自动成为伏笔或叙事债务；承诺登记须有读者期待或作者规划依据，并区分计划埋设、正文已建立与已兑现，不能把规划中的回报当作已经完成。

### 5.8 导入小说并续写

1. 作者可导入 TXT 或 Markdown 小说。
2. “导入小说并续写”与“从一个想法开始”是并列创建入口。应用验证源文件后直接创建导入型 `.zjproject`，不要求作者先建立空白项目。
3. 快速导入不调用模型，必须安全归档原始文件、识别编码、检测重复、确定性切分卷章、保留原文行范围并建立基础全文索引；完成后默认打开正文，作者立即可以阅读、编辑、新建章节和完全自行写作。
4. AI 档案生成由作者通过“AI 生成整书档案”明确启动。用户可见的目标始终是整本小说的统一档案，不是逐章档案或近期章节档案。
5. 整书档案至少包括全书/分卷/故事弧大纲、人物身份与人物弧、势力与关系、世界规则/地点/物品、全书时间线/事件/事实以及伏笔、揭示和未解线索。
6. 当整书超过上下文限制时，系统在后台自动按章节和分卷建立可恢复子任务，再执行分卷合并、全书实体统一、别名合并、冲突保留和全书综合。章节级结果只是技术中间产物和证据来源，不能作为完整小说档案呈现或入库。
7. 整书任务支持暂停、取消、断点恢复、失败步骤重试、预算上限和应用重启后的状态恢复。正文在任务运行期间保持可读写，模型调用不能阻塞正文保存。
8. 整书任务启动时冻结来源章节/revision manifest。作者在运行期间修改被冻结来源后，完成页必须列出变化范围；受影响综合完成增量重算或重新合并前，旧整书候选包不得确认入库。运行后新增章节可明确排除在本次来源快照之外，并显示档案截止范围。
9. 整书综合完成后生成一个版本化档案候选包。候选按大纲、人物与势力、世界设定、时间线与事实、伏笔与关系分类审阅，但每项都是跨整本书合并后的结论，并带多个精确章节/revision/导入行范围证据。
10. 作者可以按分类查看、编辑、拒绝和解决同名实体、别名或字段冲突。所有分类完成检查且阻断冲突解决后，作者通过一次明确操作把整书档案候选包原子确认进 canonical story archive。
11. 后续重新生成整书档案只能产生新候选版本和差异，不能静默修改已确认档案。AI 批次续写只能使用已确认档案及其明确覆盖范围；档案未完成或存在阻断冲突时必须显示限制，作者手工写作始终可用。
12. 导入原文不发送到前端以外的无关位置；UI 只加载有界正文，模型只读取作者已确认有权处理的整书来源快照。导入前必须提示用户确认其有权使用所选材料。

### 5.9 参考作品启发创作

1. 作者可提供短篇全文、精选片段、手工摘要、公开简介/百科文本或一个公开页面链接。
2. 对长篇参考，系统只读取作者明确选择的材料或指定公开页面，不自动跟踪链接或爬取原作全文。
3. AI 输出“类型与创作要素分析”，明确区分可借鉴的高层特征和禁止复用的角色、专名、设定、情节链、场景、表达。
4. 作者确认分析后，AI 生成原创方向；参考分析和发送给模型的数据范围必须可追溯。

### 5.10 模型、订阅与创作方案

1. 模型连接属于应用设置，不属于某部小说；项目只保存选用方案和运行时冻结快照。
2. 商业发布底线至少支持 OpenAI API 与 Anthropic API，并保留兼容 API、本地模型和其他运行时的统一扩展边界。
3. ChatGPT/Codex 与 Cursor 订阅连接仅可通过官方公开支持的本地 App Server、SDK、CLI 或进程协议调用；身份和凭据由官方运行时自行持有。若缺少稳定、获准且可测试的官方调用契约，该连接不得进入正式发布范围。
4. API Key 只存 macOS Keychain 或 Windows Credential Manager。
5. Codex/Cursor 的 OAuth Token、Cookie 与本地认证文件不得被应用读取、复制或写入项目数据库；应用不得解析私有协议或调用非公开端点。
6. UI 必须明确显示模型与额度来源，例如“Claude — 来自 Cursor 订阅”“GPT — 来自 OpenAI API”。
7. 不承诺任何订阅可使用所有模型；可用模型以用户账户、官方运行时、地区、版本和额度为准。
8. 从订阅运行时回退到付费 API 前必须获得作者授权。默认授权粒度为单次任务；作者可为指定项目和连接对设置带金额/Token 上限及过期时间的授权，不提供永久、无限额的全局自动回退。
9. `CreativeProfile` 支持按能力为规划、章节策划、正文写作、连续性审阅、内容编辑、文风编辑、记忆提取和影响分析选择模型；每次运行冻结所用方案。能力节点可按任务组合，不要求每次运行固定启动全部角色，也不得把角色数量或具体供应商模型写死。
10. 应用级创作方案和作者模板必须版本化。新项目记录创建时选中的默认方案版本；修改应用默认只影响后续新项目，不静默改变已有项目。项目可主动选择其他方案版本或按角色覆盖，且项目包不保存 API Key。

### 5.11 AI 作者人格与工作流模板

1. 软件支持版本化的 `AuthorProfile` 与 `AuthorTeam` 模板。
2. 模板可包含题材偏好、叙事风格、节奏约束、规划/写作/审阅分工、评价规则和适用范围。
3. 模板不包含 API Key、订阅凭据、作者正文或项目长期记忆。
4. 第一版支持本地安装、选择、导出和冻结进创作运行；在线作者市场、交易、评价和同步属于后续联网扩展。

### 5.12 导出、版本与恢复

1. 作者可导出正文和相关作品资料；导出不得修改项目正文。
2. 章节 revision、项目快照、分支与恢复草稿必须可回看和恢复。
3. 任何模型失败、应用崩溃、取消、磁盘满或迁移失败不能损坏已定稿正文和确认资产。
4. 跨 Windows/macOS 复制时必须复制完整 `.zjproject` 目录。

## 6. 交互要求

1. 产品采用“对话驱动 + 结构化结果 + 正文编辑器”。对话表达意图；结构化页面展示方案、状态、证据和确认；编辑器负责正文阅读与直接修改。
2. 工作台按权威作品状态自适应，不提供要求作者手工选择的“构建/创作/审阅”模式。创意阶段以对话和方向卡为主；作品方案/路线图阶段以结构化文档为主；批次运行阶段以队列、预算和检查点为主；批次审阅与正常写作阶段以章节队列和编辑器为主。
3. 表单只用于章节数、预算、模型选择、导入范围和影响范围等精确参数，不用于强制作者填写创意资产。
4. 作品内对话本地持久化并按阶段、章节、批次或资产筛选；对话不等同于正式项目数据。
5. 所有会产生作品修改的 AI 回复必须以候选、差异或确认动作呈现。
6. AI 面板随阶段改变默认状态：创意/方案阶段展开或可固定，路线图阶段可折叠，批次运行和正常写作阶段默认隐藏，作者审阅时按标注展开。面板切换不能丢失未发送输入或覆盖未保存正文。
7. 打开作品后，一级导航只保留创作驾驶舱、正文与章节、审阅与候选、导入与续写、作品档案、版本与交付。作品方案、故事架构、人物与势力、世界设定、时间线与事实、伏笔与关系作为“作品档案”二级页面保留。

## 7. 非功能需求

### 7.1 平台与性能

- 目标平台为 Windows 10/11 与受支持 macOS；
- 在 500 章、约 200 万中文字符、2,000 条记忆记录的合成项目上，目标章节上下文装配不超过 500ms，相关记忆首批检索不超过 200ms，打开待审阅批次不超过 500ms；
- 性能目标必须在发布前确定的 Windows/macOS 参考硬件上分别测量，并区分冷启动与热缓存。长期记忆进入正式开发前，必须使用固定 fixture 比较 SQLite FTS5、结构化索引和可选本地向量索引方案；不得依赖外部向量数据库才能达到发布目标；
- UI 不加载整本正文，按章加载有界内容；
- 长任务支持取消、重试、恢复、网络切换和应用重启后的状态重建。Wails 事件只可作为进度提示，作业状态和事件序列必须持久化；React Bridge 重新挂载、窗口恢复或应用重启后必须按 `job_id + after_sequence` cursor 增量补拉，不能依赖未丢失的内存事件。
- `.zjproject` 内部目录和文件使用固定短名或稳定 ID，不使用卷名、章名和候选标题形成深层路径；Windows 必须在未启用系统长路径选项的环境中完成创建、快照、分支、导入、导出和恢复测试。
- Windows 路径测试必须计算用户选择的项目根目录与最长内部相对路径的总长度；短 ID 不能替代总路径预算、长路径兼容和可操作的路径过长提示。
- 使用固定的多调用合成项目验证 Context Manifest 和 Invocation Artifact 的体积增长、压缩、去重、清理与中断恢复；项目打开和正文编辑不得要求全量加载历史 Prompt 或流式事件。
- SQLite 必须启用 WAL、外键和有界忙等待。数据库写入使用短事务和可取消的有界重试；模型网络 IO 不得位于数据库事务内，也不得长期持有会阻断作者正文保存、项目关闭或取消作业的工作区全局锁。是否增加写入队列或读连接池以基准测试为依据，不作为未经测量的强制实现。

### 7.2 数据安全与隐私

- 不提交、不记录、不导出 API Key、OAuth Token、凭据、用户正文、项目数据库或签名材料；
- 模型调用前清楚表明发送范围和模型连接来源；
- 错误摘要不包含正文、Prompt、模型响应、SQL 或密钥；
- 默认不需要云端账户，不上传项目包；
- 任何联网市场或遥测能力都必须另行获得作者授权。

### 7.3 内容边界与供应商政策

- 产品服务于合法的虚构创作，不把模型输出或风险扫描宣传为法律意见、平台审核结论或可发布保证；
- 作者可为项目设置年龄分级、题材边界和禁止项，并在模型调用前看到相关连接可能适用的供应商政策；
- 暴力、成人、未成年人、自伤、违法行为及其他高风险内容必须有明确的产品处理原则；涉及违法或平台禁止内容时，应用应提供可理解的限制说明；
- Provider 因内容政策拒绝时，系统必须区分“内容拒绝”和普通网络/额度错误，保留作者输入与已有候选，不得静默切换到政策或计费不同的模型；
- 切换到其他 Provider 继续任务前，必须重新展示来源、费用和可能不同的内容边界并获得确认；
- 导出前可提供可选的内容与引用风险扫描，但结果仅作作者参考。

### 7.4 可用性与可访问性

- 新作者无需理解 Provider、Token、上下文窗口或智能体角色即可开始创作；
- 高级细节按需展开；
- 支持键盘导航、可预测焦点、文本化状态、非颜色唯一提示与 Windows/macOS 快捷键；
- 关键确认、覆盖和费用操作必须明确可见且可取消。

### 7.5 质量与可验证性

- 领域、应用、持久化、运行时和 UI 均有自动测试；
- 真实模型 API 不进入 CI；
- 创作质量与长篇连续性使用两套独立 Harness：前者验证“写得是否可接受”，后者验证“记得是否正确、上下文是否充分”；任何单项通过都不能代替另一项。
- 创作质量 Harness 使用固定原创题材、创意种子、作品规格和章节任务，保存模型、参数、Prompt、工作流与输出 Schema 版本，并对比单次直出、智能体初稿和审阅修订稿。
- 自动创作门禁至少检查结构、字数、锚点、格式、重复和机械句式；人工盲评至少覆盖开篇钩子、阅读驱动力、情节推进、信息密度、人物动机、人物声音、场景化表达、因果、冲突、情绪递进、可读性和原创风险。
- “没有 AI 味”不能由单一 AI 检测器或单个模型评分证明。确定性检查只作为写作 lint，最终质量以目标作者/编辑盲评、候选接受率、局部修改率和整章重写率为准。
- 创作质量回归必须覆盖上下文漏召回后的补查、人物谎言/猜测误判、审阅争议、文风修订改变知识边界、修订引入新冲突、前一候选保留、补查/修订预算耗尽和恢复；分别报告硬冲突漏检、误报、修订解决率、新问题率、费用与作者修改时间。新增独立模型节点须通过与最小工作流的质量、失败率和成本对照，不以 Agent 数量作为收益。
- 长篇叙事验收需在原创连续创作样本上评估章节作用、重复冲突、故事弧回报、人物变化、伏笔兑现与终局推进，记录每万字可接受正文的模型用量、费用、等待和作者修改时间。检索召回测试不能替代叙事质量验收；样本规格与题材分项门槛须在运行前冻结。
- 对应创作能力未通过质量 Harness 前，不进入完整上层业务界面开发；此阶段只允许模型配置、Agent 运行观察、候选审阅和人工评分所需的薄界面。
- 使用合成长篇与 fake Provider 验证长篇记忆、批次状态、影响分析和恢复；
- 合成长篇由确定性生成器、固定种子和可审计的黄金事实/查询清单构建，不使用有版权风险的真实小说。每个 PR 运行缩小版正确性集，完整 500 章 Harness 在 Nightly、Release 和稳定参考 Runner 上运行；共享 CI 的不稳定墙钟时间不得成为唯一性能判据。
- fake/Recorded Provider 用于验证 Agent 状态流、错误和恢复；纯检索与 Context Manifest 装配基准不得依赖模型调用。
- 自动测试必须覆盖 JobEvent 的漏推、重复、乱序防护和 cursor 补拉，模型调用期间的正文并发保存，以及第二实例占用、同步目录锁定和 Windows 路径边界。
- Windows/macOS 均需完成 production build 与人工验收。
- 商业发布前必须完成不少于 8 名目标作者的封闭可用性测试，其中至少 3 名具有 50 章以上长篇写作经验；记录首次正文时间、候选接受/重写率、批次完成率、恢复成功率、费用理解和连续性问题，并关闭阻断创作或可能损坏作品的问题。

## 8. 版本范围

### 8.1 首个商业发布底线

- 创意到作品方案、全书路线图、批次候选、审阅定稿的闭环；
- 默认 3–10 章批次、章级审阅、跨章检查点、熔断、定稿和记忆更新；
- 创作锚点、候选隔离、Context Manifest 和已定稿历史保护；
- 本地 `.zjproject` 创建、打开、revision、基本快照、恢复、导出和双平台数据保护；
- 可恢复 JobEvent feed、Bridge 重挂载补拉、模型调用期间正文保存，以及项目跨进程写入互斥；
- OpenAI API 与 Anthropic API、OS 凭据库、任务级预算与费用来源显示；
- TXT/Markdown 快速导入、确定性切章、整书档案后台分段与全书聚合、跨章节证据确认和整包入库；
- 中等篇幅合成项目上的连续性、恢复和性能发布门槛。
- 固定创作质量测试集上的结构门禁、人工盲评、候选接受率和重写率达到发布前确定的题材分项门槛；不得以自动平均分掩盖正文可读性或人物表现退化。

### 8.2 完整 V1 目标能力

- 单批最多 50 章的高级范围与长批次检查点；
- 500 章合成长篇 harness 和量化连续性验收；
- 整书档案后台分段处理、断点恢复、全书实体聚合、冲突保留和来源覆盖管理；
- 满足官方协议、许可、兼容性与契约测试门槛的 Codex/Cursor 订阅运行时；
- 本地 AuthorProfile/AuthorTeam 模板；
- 命名快照、剧情分支、跨平台完整恢复和长任务硬化。

8.2 中的单项能力未达到发布门槛时，可以延后到兼容的 V1.x 更新，但不得削弱 8.1 的作者主权、数据安全、候选隔离和可恢复性。

### 8.3 明确不属于 V1

- 在线 AI 作者市场、付费、交易、评价、云同步和多人协作；
- 平台代付模型额度或共享订阅额度；
- 自动发布到小说平台；
- 自动抓取或全文复现第三方小说；
- 外部向量数据库和云端必需服务；
- 未经单独架构决策的 Rust、CGO/FFI 或 Wails v3。

## 9. 产品验收

### 9.1 商业发布阻断验收

1. 一句中文创意可得到三套原创方向、完整作品方案与全书路线图；
2. 作者可从方案启动默认 3–10 章批次，设置锚点，并在检查点暂停、处理风险和逐章定稿；
3. 批次熔断后，作者可从未定稿位置回退生成进度；下游候选被标记为已取代而非删除，新的 attempt 使用更新后的锚点和 Context Manifest，canonical 正文保持不变；
4. 作者对第 7 章提出意见后，系统先给影响方案，只处理受影响候选；
5. 作者修改已锁定的高层设定时，系统区分未来生效、故事内演变和追溯修正，列出历史定稿冲突及待解决的未定稿内容，不自动改写历史；
6. 已定稿历史和确认资产不会被 AI 自动改写；记忆提取失败不影响正文安全定稿；
7. 导入小说完成确定性切章后正文立即可读写；作者可启动整书档案生成，系统后台分段但最终只呈现带跨章节证据的全书聚合档案候选，并在作者解决冲突后整包确认入库；
8. API 连接显示真实来源、预算和实际用量；失败、内容拒绝或额度耗尽不会静默切换到其他模型或收费来源；
9. 应用重启、取消、失败、磁盘满或数据库迁移后，定稿正文、确认资产与项目包保持可恢复；
10. 项目瘦身后仍可通过长期 Manifest、不可变来源和哈希解释 canonical revision 的上下文组成，且不会删除正文、候选或必要证据；
11. 长任务执行期间模拟 React Bridge 重新挂载、事件漏推和重复推送后，界面能按持久化 cursor 补拉并重建与数据库一致的状态，不重复应用步骤或丢失待确认动作；
12. 模型调用期间作者仍可编辑和保存正文；任何 Provider 延迟、取消或失败不得通过数据库事务或工作区全局锁长期阻塞保存；
13. 同一 `.zjproject` 被第二应用实例打开时，系统阻止并发写入并提供可理解的重试、只读或恢复副本路径；同步目录运行期锁定不得损坏 canonical 内容；
14. Windows 与 macOS 上均通过本地项目创建、编辑、导入、恢复、模型连接、长任务和默认路径长度场景验收；
15. 封闭作者测试未发现阻断创作、误导收费或可能损坏正式作品的未解决问题。
16. 在固定原创测试集上，智能体审阅修订稿相对同模型单次直出具有可记录的盲评提升；产品能够显示并回溯对应的模型、Prompt、工作流、输入版本、审阅结论和用量。
17. 缺关键证据时只执行授权内补查并记录新上下文版本；补查失败、争议或预算耗尽不伪造事实，不产生未授权调用，恢复不重复执行结果未知的操作。
18. 最终候选通过绑定该版本的复检；文风修订、部分采纳或作者编辑后不继承失效的通过结论。修订退化可保留有效前稿，无合格候选时停止并保留问题。
19. 定稿中的谎言、猜测、梦境及后续揭示不会被直接固化为世界事实；普通细节不强制登记为承诺，后验失败不回滚正文，旧来源变化后相关解释正确失效。
20. 批次与故事弧评估能识别无实质推进、重复冲突和承诺未兑现，并输出带范围、依据和费用的规划候选；高层路线图未经作者确认保持不变。

### 9.2 长篇连续性量化验收

在固定的 500 章合成项目和不少于 100 个预置查询的测试集中：

1. 锁定硬约束、人物当前状态和重要事实的 `Recall@10` 不低于 95%；
2. 未兑现伏笔和跨卷重要承诺的 `Recall@10` 不低于 90%；
3. 返回证据中能直接支持所召回事项的比例不低于 90%；
4. 已失效状态被当作当前事实召回的比例不高于 5%；
5. 第 1 章预置的重要承诺必须出现在第 500 章对应测试场景的 Context Manifest 中，并指向正确章节/revision 证据；
6. 所有 Context Manifest 均满足任务 Token/字符预算，且达到 7.1 的本地检索与装配性能目标。

指标按任务类型分别报告，不能以简单平均掩盖硬约束、伏笔或当前状态中的单项失败。

Harness 必须由固定种子、生成规格和黄金事实/查询清单可重复构建，并分别记录冷启动、热缓存、Context Token/字符占用、项目包体积和 Invocation Artifact 清理前后体积。PR 级缩小集负责快速正确性回归，完整 500 章集负责 Nightly/Release 的召回、体积和参考硬件性能门槛。
