# 小说项目恢复与数据保护

本说明适用于织境 Story Studio 的 `.zjproject` 本地项目包。项目包包含正文数据库、附件、导出结果、剧情分支和快照目录；复制、备份或恢复时必须把整个目录作为一个整体处理。

## 先保护原件

1. 退出织境，确认没有仍在保存的窗口。
2. 在 Finder 或 Windows 文件资源管理器中复制整个 `书名.zjproject` 目录。
3. 给副本加上日期，例如 `书名-恢复副本-YYYY-MM-DD.zjproject`。
4. 后续排查只打开副本，保留原件不动。

不要单独复制正在使用的 `project.db`，也不要手工编辑 `.db`、`.db-wal` 或 `.db-shm` 文件。应用在打开现有项目时不会创建缺失数据库，也不会自动覆盖损坏库或未来版本库。

## 项目被另一实例编辑时

每个项目包使用固定的 OS lease 保证同一时刻最多只有一个可编辑进程。发现占用时，应用不会尝试删除锁文件或覆盖正在编辑的内容，而会提供四个安全选项：

- **重试**：原编辑器已正常退出后，再次请求可编辑 lease。
- **只读打开**：查看正文、资产和历史；不会迁移旧 Schema、恢复中断操作、启动后台作业或保存任何草稿/正文。
- **创建恢复副本**：选择目标父目录，应用从源项目生成一个新的、已校验的 `.zjproject` 包并尝试打开它；原件始终保持不变。若自动打开失败，记录副本路径后可手动重新打开。
- **取消**：回到当前工作区或欢迎页，不改变源项目。

`project.lease` 文件中的 JSON 只是占用诊断信息，**不是锁的真实性来源**。即使它残留或看起来过期，也不要手工删除：另一个进程仍可能持有 OS lock。应先确认其他织境窗口已退出，再使用“重试”或从系统重新打开项目。

只读模式不能升级旧 Schema，也不能绕过待恢复的迁移、快照或分支 journal；遇到这类提示，请使用与项目匹配的版本在可编辑模式完成恢复，或先创建恢复副本。SQLite 为读取活跃 WAL 可以维护 `project.db-shm` 或创建空协调文件，这不表示应用写入正文、资产或恢复数据。

## 中断后的恢复草稿

正文有两层保存：

- 恢复草稿：输入停止约 200ms 后写入，用于进程或系统中断后的短周期恢复。
- 已提交正文：输入停止约 750ms 后形成新 revision，上一 revision 会进入历史记录。

正常关闭窗口时，应用会先等待当前章节的最后一份草稿或正文提交完成，再退出；如果最终写入失败，窗口会保持打开并保留编辑器中的本地文本。

重新打开含恢复草稿的章节时，应用同时保留已提交版和恢复草稿，并显示两者的保存时间与字数。可选择：

- “恢复草稿”：把草稿放回编辑器，随后按正常流程提交为新 revision。
- “保留已提交版”：二次确认后只删除恢复草稿，不修改已提交正文。
- “稍后决定”：恢复草稿继续保留，正文保持只读；可随时重新打开恢复选择。

发生 revision 冲突时，本地文本不会被静默替换。先保留本地文本，再重新加载最新已提交版进行人工比较。

## 切换或关闭项目时的长任务

续写、审校和设定抽取等作业会调用模型 Provider，属于长任务。切换项目、关闭窗口、恢复快照或切换分支时，应用不会立即关闭数据库，而是按以下顺序保护数据：

1. 标记工作区为 draining，拒绝启动新的续写或抽取作业；
2. 向仍在运行的作业发送取消信号，并等待它们释放作业租约（job lease）；等待有界超时，避免阻塞作者；
3. 租约全部释放或超时后，应用才关闭旧数据库并切换到新的活动工作区。

作业在模型调用期间不持有工作区全局锁，因此作者在此期间仍可保存恢复草稿、新建章节或执行其他编辑操作。

如果某个作业因网络阻塞未能及时退出，超时后它的租约会被标记为 stale。此时旧数据库已被关闭，作业不会向已关闭的数据库回写，而是转入 `recoverable`（可恢复）状态并保留已经生成的中间产物。作者可以在新活动项目上重试该作业，重试会创建一条新的作业记录，不会覆盖已提交正文。

- `recoverable` 作业不会自动重跑；作者在作业面板看到“可恢复”提示后可手动重试。
- 重试在新活动 store 上执行，不写旧 generation 的已关闭数据库。
- 作业退出只记录 run/step 状态，不会让 canonical 正文或已确认资产进入不一致状态。

## JobEvent 事件源与 cursor 恢复

续写、审校和抽取作业从创建时就写入 `job_queued`，随后每一次状态变化（启动、步骤开始/完成/失败、作业完成/失败/取消/恢复）都作为 append-only `JobEvent` 写入 `job_events` 表，每个作业按 `(job_id, sequence_number)` 单调递增。同一事务还会刷新 `job_snapshots` 表中的权威投影（状态、`max_sequence`、`earliest_replayable_sequence`、累计 token 用量、步骤状态、待确认动作和终态信息）。事件只携带轻量 JSON 摘要，生成的大文本进 artifact，不复制正文。

应用重启或 Bridge 重挂载时，UI 不重放整条事件流水线，而是按 cursor 增量补拉：

1. 作业面板通过 `ListRecoverableJobs` 发现非终态（running/queued/recoverable）及待确认作业；
2. 对每个作业调用 `GetJobEvents(jobID, afterSequence, limit)`，按 sequence 升序返回一页事件，附带 `next_cursor`、`has_more` 与 `snapshot_required`；
3. React reducer 按 `(job_id, sequence_number)` 幂等应用事件——已应用的事件跳过，遇到 `sequence > cursor + 1` 的缺口时停止并从缺口前一条补拉，保证重复通知或漏推不会导致状态不一致；
4. 当 cursor 早于 `earliest_replayable_sequence`（事件已被清理）时 `snapshot_required` 为 true，前端先用 `GetJobSnapshot` 重建状态并把 cursor 重置为 `max_sequence`，再继续补拉。

项目重开时，`RecoverInterruptedAgentRuns` 与 `RecoverInterruptedTasks` 会把仍处于 running 的作业转入 `recoverable`，并在同一事务内为每个被恢复的作业 append 一条 `job_recovered` 事件、刷新 `JobSnapshot`。这样事件流水的终点与权威投影一致：作者重开项目后，作业面板会看到“可恢复”状态和完整的恢复事件链。已终态（completed/failed/cancelled）的作业不会获得 `job_recovered` 事件。

Wails `job:updated` 通知只发送 `job_id + latest_sequence`，允许丢失、合并或重复——正确性由 cursor 补拉保证，不依赖通知到达次数。累计 token、费用或章节数只来自 `JobSnapshot` 或事件 payload 中的权威字段，不会根据通知次数累计。

## 版本历史与项目快照

“版本历史”页面提供两种恢复粒度：

- 章节版本：可以对比历史正文和当前正文。恢复旧版本时，当前正文先进入历史，旧内容再保存为一个编号继续递增的新 revision；已有版本不会被删除或重写。
- 项目快照：命名快照会一致性保存当时的整个 `project.db`，覆盖正文、人物、势力、大纲、世界设定、时间线和事实等数据库内容。

恢复项目快照前，应用会自动创建“恢复前”快照，然后关闭当前数据库并执行可回滚替换。恢复库通过完整性与项目身份校验后才会成为当前工作区；若校验或重新打开失败，应用会恢复原数据库。若进程在替换中途终止，下次打开项目会优先恢复替换前数据库。

项目快照位于 `.zjproject/snapshots/`，每个快照由只读用途的 SQLite 副本和元数据组成。不要手工重命名、删除或配对这些文件。跨设备备份仍需复制完整 `.zjproject`，否则快照历史不会一同迁移。

## 剧情分支

“版本历史”页面中的剧情分支会隔离整部作品的正文和全部结构化故事资产。当前活动状态仍使用根目录的 `project.db`，分支注册表和完整分支头位于 `.zjproject/branches/`。

- 切换分支前，应用会先一致性备份当前数据库到当前分支头，再激活目标分支。
- 合并前，应用会先创建自动恢复快照；第一版只允许子分支向未发生额外变化的直接来源分支严格快进合并。
- 如果来源分支在分叉后也发生变化，应用会阻止合并，不会覆盖任一侧数据。
- 切换或合并使用外部事务日志、暂存文件和恢复备份。若进程在操作中止，下次打开项目会根据已原子提交的分支注册表决定完成操作或恢复原数据库。

不要手工编辑或删除 `branches/index.json`、`branches/heads/` 及操作中的 `.branch-*` 文件。需要移动、复制或恢复项目时，必须保持整个 `.zjproject` 目录内部文件一致。

## 项目无法打开

应用会在激活项目前依次检查项目目录、SQLite 文件头、Schema 版本、迁移、`PRAGMA quick_check` 和唯一项目记录。失败时，当前已打开项目仍保持不变。

- 项目不存在：检查项目目录是否被移动、重命名或断开外接磁盘；重新选择实际 `.zjproject` 目录。
- 无权限或只读：先复制项目包到当前用户可读写的位置，再打开副本。不要直接修改公司共享盘或只读备份的权限。
- 数据库损坏：立即保留原件并使用副本排查；不要用空数据库替换 `project.db`。优先从可信备份或快照恢复。
- 项目版本过新：使用创建该项目的相同或更新版本打开；旧版本不会降级或改写数据库。
- 项目被占用：关闭其他织境窗口或占用该项目的备份工具，稍后重试。锁等待失败不会留下部分草稿提交。
- 磁盘写入失败：检查剩余空间、目录权限和同步盘状态；在恢复写入能力前不要继续大量编辑。
- 迁移现场无法判定：应用提示“迁移恢复需要人工介入”时，保留整个 `.zjproject` 目录并联系支持；不要手工删除 `recovery/` 中的任何文件。

## 旧项目升级迁移

打开旧版本 Schema 的项目时，应用不会直接在原库上执行迁移，而是按以下安全流程操作：

1. 先对原库执行 `quick_check`、读取 Schema 版本和唯一项目 ID；
2. 使用 SQLite `VACUUM INTO` 在 `recovery/` 创建一致性升级前备份；
3. 将备份复制为 stage 数据库，在 stage 上执行 Goose 迁移和校验；
4. 校验通过后，用带 journal 的原子 rename 序列替换 `project.db`；
5. 重新打开新库并验证 Schema、`quick_check` 和项目 ID；
6. 全部通过后才替换当前工作区。

### 升级前备份

`recovery/migration-v09-v14.sqlite` 是升级前的一致性备份，成功升级后仍保留，用于支持恢复。它不是用户命名的快照，不出现在“版本历史”列表中。

### 迁移失败与中断恢复

- stage 迁移或校验失败：原 `project.db` 不被修改，stage 和 journal 被清理，备份保留。
- 激活后重新打开失败：原库从 `migration-original.sqlite` 恢复为 `project.db`，新库和 stage 被删除。
- 进程在迁移中途终止：下次打开项目时，应用按 journal phase 自动恢复原库或确认已提交的新库。
- journal 损坏或文件组合无法判定：应用返回“迁移恢复需要人工介入”，不删除任何可能是唯一副本的数据库文件。

`recovery/` 是内部恢复目录，不属于用户可见的快照或导出。跨设备备份仍需复制完整 `.zjproject` 目录。详见[旧项目迁移测试基线](../testing/legacy-project-migration.md)。

## 跨平台注意事项

- 在 Windows 与 macOS 之间传递时始终复制完整 `.zjproject` 目录。
- 不要在传输过程中打开项目；等待同步工具完成全部文件后再打开。
- 恢复时不要让同步工具、杀毒软件或另一个应用窗口占用 `project.db`；Windows 文件锁会安全阻止替换并保留原数据库。
- Windows 项目名称会避开系统保留名，macOS 上也不要手工改成 `CON`、`NUL`、`COM1` 等名称。
- 提交给支持人员前先制作副本；项目正文属于用户私有内容，未经明确授权不得上传。
