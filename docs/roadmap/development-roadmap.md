# 织境 Story Studio 总体开发路线图

- 状态：已批准
- 更新日期：2026-08-12（R1 与 R2 已完成，下一阶段为 R3 正式资产写入）
- 适用范围：当前商业发布底线与完整 V1
- 上游依据：[产品需求](../product/requirements.md)、[产品与交互设计](../product/design.md)、[系统技术设计](../architecture/system-design.md)
- 实施计划规范：[实施计划目录说明](../plans/README.md)

## 1. 路线图用途

本路线图定义从当前代码基线走向商业发布底线和完整 V1 的实现顺序、阶段依赖与退出标准，不提供工期承诺，也不替代产品需求、交互设计、系统技术设计或架构决策。

路线图只回答：

- 下一阶段应该解决什么；
- 为什么必须按此顺序推进；
- 哪些能力可以复用当前实现；
- 达到什么证据后才能进入下一阶段；
- 应为哪些独立能力建立实施计划。

每项具体能力在开始开发前单独编写实施计划。实施计划必须引用本路线图阶段及对应需求条款，不能在任务清单中重新定义产品范围。

## 2. 推进原则

1. **纵向切片**：每个阶段同时覆盖必要的领域、应用、持久化、Wails binding、React 和测试，不按技术层一次铺完。
2. **可靠性先于扩量**：先保证长任务、项目锁、定稿和恢复不会损坏作者数据，再扩大批次数、长篇规模和模型连接。
3. **商业闭环先于高级能力**：先完成 API 模式下的创意、方案、路线图、3–10 章批次、审阅和定稿闭环，再实现 50 章高级批次、订阅运行时和模板市场方向。
4. **复用现有纵切**：正文/revision、结构化资产、ChangeSet、快照/分支、Provider、Agent Run、导入和基础抽取作为实现基线保留；发现正确性缺口时就地修复，不平行重写第二套系统。
5. **候选与正式资产隔离**：作品方案和整书档案候选包只在各自审阅流程中展示；作者整包确认后才写入对应正式资产页面和 canonical memory。
6. **一个计划解决一个边界清晰的能力**：大型阶段拆成多个可独立验收的实施计划，不创建覆盖整个产品的巨型计划。
7. **证据驱动过关**：阶段完成以自动测试、迁移验证、性能记录、双平台构建或人工验收证据为准，不以代码数量或页面完成度判断。

## 3. 当前实现基线

当前仓库已经具备：

- Go + Wails v2 + React/TypeScript + Vite + SQLite 的生产骨架；
- 本地项目创建/打开、章节正文、revision、恢复草稿；
- 人物、势力、世界、故事结构、时间线、事实和伏笔等结构化资产；
- ChangeSet、项目快照、剧情分支；
- OpenAI/Anthropic API、凭据适配和基础 Agent Run；
- TXT/Markdown 导入、确定性切章和基础资产抽取；
- SQLite WAL、5 秒 busy timeout、Goose 迁移与基础完整性检查。

当前关键缺口包括：

- 应用级 `settings.db`、模型方案版本、最近项目和主题偏好；
- 原生系统菜单、最近项目首页和作品打开后的独立项目壳；
- 分级作品导航、权威 WorkbenchProjection 和阶段自适应 AI 面板；
- 模型连接/角色配置仍与项目任务页面混合，项目级旧配置尚未迁移；
- 原创“创意 → 方案 → 路线图 → 批次 → 定稿”产品状态机；
- 检查点、熔断、回退生成和 GenerationAttempt；
- 轻量 Context Manifest、长期记忆与分层 Harness；
- 整书档案父任务、全书实体聚合、冲突保留和整包确认；
- 双平台 Release CI、签名、公证、安装与升级验证。

## 4. 阶段依赖

```text
R0 基线与 CI
  → R1 长任务与项目可靠性
  → R2 产品壳、应用设置与交互基础
  → R3 正式资产写入与导入正确性
  → R4 原创创作前半闭环
  → R5 3–10 章批次创作闭环
  → R6 Context Manifest 与长篇连续性
  → R7 高层设定变更与影响分析
  → R8 整书档案生成与全书聚合
  → R9 项目空间、跨平台与商业发布硬化
  → R10 完整 V1 增强能力
```

单人开发默认按上述主链顺序推进。阶段内部只有在数据模型、迁移和公共接口互不依赖时才并行；不得为了并行而复制领域模型或创建临时旁路。

## 5. R0：固定基线与 CI

### 目标

建立后续所有改动的可重复验证入口，确保当前纵切和旧项目迁移不会在新开发中无声退化。

### 范围

- 固定 Go、React、SQLite 迁移、Provider、导入、快照与分支测试基线；
- 建立不依赖真实 API Key 的 fake/Recorded Provider 测试入口；
- 建立 Go 测试、前端测试、绑定校验和生产构建任务；
- 在 Windows/macOS 原生 Runner 上验证 Wails 构建；
- 建立旧项目 fixture、迁移和恢复检查；
- 把双平台手工验收清单纳入 Release 流程；
- 明确 CI 与 Release CI 的分层，签名、公证和正式安装验证留到 R9。

### 退出标准

- 普通提交可以自动运行不含真实模型调用的核心测试；
- Windows/macOS Runner 可以生成可检查的生产构建；
- 数据库迁移和旧项目打开有自动回归保护；
- CI 失败能够定位到 Go、前端、迁移、绑定或打包阶段；
- 仓库不上传凭据、真实作者正文或本地项目数据库。

## 6. R1：长任务与项目可靠性

### 目标

让所有后续 AI 工作流具备可取消、可恢复、可补拉且不阻塞作者保存的运行基础，并防止多个进程同时写同一项目。

### 范围

#### R1.1 Agent 生命周期与锁隔离

- 移除跨 Model IO 的工作区全局锁；
- 引入 project/store generation 和 job lease；
- 项目切换、关闭、恢复时拒绝新作业并取消或等待已有作业；
- Provider 调用期间允许作者编辑和保存正文；
- 防止作业向已关闭 store 回写。

#### R1.2 可恢复 JobEvent

- 建立 `JobEvent`、`JobSnapshot` 和单调 sequence；
- 状态变化与事件在同一短事务提交；
- 实现作业快照、增量事件和可恢复作业查询；
- Wails Event 只发送轻量更新通知；
- React 按 cursor 补拉、检测缺口并幂等更新；
- 覆盖重挂载、重复通知、漏推、应用重启和事件清理后的 snapshot 重建。

#### R1.3 项目生命周期保护

- 项目级 OS 文件锁；
- 第二实例禁止并发写入；
- 建立不会迁移、checkpoint 或启动后台任务的只读 store；
- 提供重试、只读打开和恢复副本；
- 覆盖活跃 WAL 只读、恢复副本一致性和残留锁元数据。

#### R1.4 Windows 文件锁、写入探针与路径边界

- 建立包目录、SQLite 短写入/回滚、WAL/SHM、checkpoint 与同目录原子替换探针；
- 对同步盘和网络映射目录提供非阻断风险提示，并分类处理运行期 sharing violation；
- 完成 Windows 默认 MAX_PATH 环境下的路径预算、保留名、短 ID 和可操作错误；
- 验证同步目录锁定、原子替换失败和长根路径不会损坏 canonical 内容。

### 退出标准

- 可阻塞 fake Provider 运行期间正文保存仍成功；
- Bridge 重新挂载或漏掉 Wails Event 后，UI 能从持久化 cursor 恢复一致状态；
- 项目关闭或切换后没有后台作业继续写旧 store；
- 第二实例不能同时写入同一项目；
- 强制取消、进程中断和锁冲突不改变 canonical 内容。

### 待建立实施计划

2. [R1 可恢复 JobEvent feed](../plans/2026-08-06-r1-recoverable-job-event-feed-implementation.md)（`completed`）

R1.1 已完成并通过三平台 Foundation CI（run `31089401016`：Ubuntu race/vet、macOS 生产构建、Windows 完整 Go tests 与生产构建）。Agent 与抽取作业的 Provider 调用不再持有工作区全局锁，作者可在模型 IO 期间保存草稿与新建章节；项目切换/关闭先 drain job lease 再关闭 store，generation 安全网保证作业不向已关闭 store 回写，超时作业转入 `recoverable` 供作者重试。R1.2–R1.4 按其退出标准依次推进。

## 7. R2：产品壳、应用设置与交互基础

### 目标

先建立后续产品能力共同依赖的桌面应用壳、应用级设置、项目导航和阶段工作台边界，使 R3 之后的资产、原创、批次和整书档案功能进入正确位置，而不是继续堆叠在当前单页工作台。

### 范围

#### R2.1 应用设置与偏好存储

- 建立应用数据目录下的 `settings.db`、版本化迁移和 repository/application service；
- 保存非敏感模型连接元数据、CreativeProfile/AuthorProfile 版本、最近项目、主题和高级偏好；
- API Key 继续只存操作系统凭据库；
- 建立旧项目内 provider/profile 配置到应用设置的可恢复迁移；
- 项目只保存创作方案版本选择、角色覆盖和运行冻结快照；
- 修改应用默认只影响新项目，已有项目必须主动升级。

#### R2.2 原生菜单与首页

- 建立 macOS 原生应用菜单和 Windows 功能等价菜单；
- 软件名称菜单只承载应用操作，“文件”承载项目生命周期操作；
- 首页显示原创、导入、打开和最近项目；
- 最近项目可直接安全打开，失效路径可重新定位或移除；
- 没有最近项目时显示欢迎引导；
- 首页不读取所有项目数据库，也不显示模型配置和故事资产。

#### R2.3 作品导航与工作台投影

- 打开作品后以作品导航替换首页左栏；
- 一级导航固定为创作驾驶舱、正文与章节、审阅与候选、导入与续写、作品档案、版本与交付；
- 现有故事架构、人物、世界、时间线、候选、版本和导出页面迁入对应二级入口，不删除现有能力；
- Go 应用层提供权威 `WorkbenchProjection`，React 不根据路由猜测产品阶段；
- 导航数量、只读、文件系统风险和可恢复任务使用服务器权威状态。

#### R2.4 阶段画布与 AI 面板框架

- 建立创意方向、作品方案/路线图、批次运行、作者审阅和正常写作五类画布容器；
- 当前尚未实现的业务阶段显示明确的未就绪状态，不伪造结果；
- AI 面板按阶段默认展开、可折叠、按标注打开或隐藏；
- 正常写作支持选中文字、上下文动作和 `Cmd/Ctrl+J` 呼出入口；
- 面板和画布切换不丢失未发送输入或未保存正文；
- 将当前 AgentWorkbench 拆为应用级模型设置、项目方案选择和项目任务运行三个边界。

#### R2.5 导入入口与整书档案交互壳

- “导入小说并续写”作为首页和“文件”菜单的独立创建入口；
- 快速导入完成后默认打开正文，保留现有确定性切章能力；
- 正文立即可读写，并显示整书档案尚未生成的非阻断状态；
- 建立“AI 生成整书档案”的应用命令、状态 DTO 和未实现能力的安全禁用边界；
- 整书档案实际后台聚合留给 R8，但 R2 先固定入口、页面位置、权限和状态契约，避免后续再次改应用壳。

### 明确不包含

- 不在 R2 实现三方向、完整作品方案、路线图或批次生成业务；
- 不在 R2 实现整书实体聚合和档案候选生成；
- 不在 R2 改变 canonical/candidate、批次或长期记忆规则；
- 不用静态假数据把未实现业务表现为已完成。

### 退出标准

- 无项目打开时可以配置应用级模型连接和默认创作方案；
- 新项目记录默认方案版本，修改全局默认不会改变已有项目；
- 首页最近项目、欢迎状态、原生菜单和安全打开路径通过 React、Go binding 与双平台冒烟验证；
- 打开作品后只显示作品导航，现有正文、资产、导入、候选和版本功能仍可到达；
- React 使用权威 WorkbenchProjection 选择画布，阶段和待审阅数量在重挂载后保持一致；
- 正文阶段 AI 面板默认隐藏且可安全呼出，切换面板不丢失编辑；
- 导入完成后正文立即打开，整书档案入口存在但在后端能力未完成时不会伪造成功；
- 旧项目模型配置迁移、失败回滚和 OS 凭据引用具有自动测试。

### 待建立实施计划

1. [R2 产品壳与交互基础](../plans/2026-08-11-r2-product-shell-interaction-foundation-implementation.md)（`completed`）

R2 产品壳与交互基础已完成并通过全部自动门禁与双平台手工冒烟（F-19 至 F-25）。应用级 `settings.db`、模型连接元数据、CreativeProfile 版本、最近项目首页、原生菜单、分级作品导航、权威 `WorkbenchProjection` 和阶段自适应 AI 面板均已就位；旧项目 provider/profile 配置可幂等迁移到应用设置且失败可回滚，API Key 继续只存 OS 凭据库。首页"导入小说并续写"完成后正文立即可读写；整书档案入口存在但在 R2 返回 `FEATURE_NOT_AVAILABLE`，不伪造成功。R2 阶段完成，可进入 R3。

## 8. R3：正式资产写入与整书档案确认

### 目标

让 AI 作品方案和整书档案候选包在作者确认后，通过同一组应用用例写入现有正式资产页面；未确认候选不进入正式资产列表或 canonical 上下文。

### 范围

- 定义作品方案 revision 与整书 `ArchiveCandidateBundle` 到现有大纲、人物、势力、世界、时间线、事实、关系和伏笔存储的映射；
- 复用现有资产表与应用服务，不平行创建第二套资产数据库；
- 作品方案和整书档案确认复用统一的原子事务、幂等键与失败回滚，重复调用不能创建重复资产；
- 正式资产记录来源方案 revision、整书档案版本、导入任务及一处或多处原文证据；
- 整书候选按档案类别显示审阅状态、别名、冲突、时间演变与来源覆盖，不以章节候选作为用户确认单位；
- 未确认候选只在作品方案、整书档案和 ChangeSet 审阅流程中显示；
- 修复现有基础抽取链路中的正文持久化、ContextCharBudget、部分重试、冲突保留、证据范围和 `create_*` 应用映射问题，为 R8 的全书聚合复用。

### 退出标准

- 作品方案确认后，相应信息可在各正式资产页面查看和编辑；
- 整书档案候选包确认后，相应信息可在各正式资产页面查看和编辑；
- 未确认候选不会出现在正式资产页面，也不会进入后续 canonical 上下文；
- 整包确认具备事务原子性，重复确认和任务重试不会创建重复正式资产；
- 每项导入正式资产可以回看跨章节或跨卷的精确原文证据。

### 待建立实施计划

1. `R3 作品方案正式资产映射`
2. `R3 统一资产确认事务与幂等`
3. `R3 整书档案候选包映射`
4. `R3 跨章节证据、冲突与整包确认`

## 9. R4：原创创作前半闭环

### 目标

完成“一句创意 → 三套方向 → 作品方案 → 正式资产 → 全书路线图”的可恢复原创流程。

### 范围

- 建立原创作品阶段状态机；
- 生成、比较、重做、组合和选择三套原创方向；
- 从选定方向生成可编辑、可锁定的结构化作品方案；
- 作品方案确认后调用 R3 的正式资产写入路径；
- 生成全书、卷、故事弧和章节范围路线图；
- 支持硬锚点、软锚点和禁止项；
- 所有 AI 操作使用 R1 的 JobEvent、预算、取消和恢复协议。

### 退出标准

- 一句中文创意可以完成三方向比较和作品方案确认；
- 确认资产出现在对应正式页面；
- 路线图确认后作品进入 `ready_to_write`；
- 任一阶段重启应用均可恢复状态，不依赖聊天内存；
- AI 不会静默覆盖已确认方案或锁定资产。

### 待建立实施计划

1. `R4 原创作品状态机`
2. `R4 三方向生成与比较`
3. `R4 作品方案编辑、锁定与确认`
4. `R4 分层路线图与创作锚点`

## 10. R5：3–10 章批次创作闭环

### 目标

完成首个真正可用于持续写作的正文闭环：批次规划、生成、审阅、检查点、作者救局、逐章定稿和下一批。

### 范围

- 默认 3–10 章批次和单作品/分支单活跃批次约束；
- 冻结 canonical head、路线图、锚点、模型和预算；
- 按章节执行计划、正文、自动审阅、必要修订和候选持久化；
- 同批前序候选只能以 provisional 身份进入后序上下文；
- 连续性、人物知识、因果、节奏、世界规则和伏笔审阅；
- 默认每 3–5 章创建检查点；
- 阻断条件进入 `needs_confirmation`；
- 支持修正继续、回退生成、接受风险和结束批次；
- 回退创建新 `GenerationAttempt`，旧候选标记 `superseded`；
- 作者逐章编辑、废弃或定稿；
- 记忆抽取失败时安全定稿并记录 `memory_pending_rebuild`。

### 退出标准

- 真实的 3–10 章批次可以完整运行和逐章定稿；
- 取消、失败、重启、熔断和回退均不破坏 canonical 内容；
- provisional 信息不会进入正式长期记忆；
- 当前批次未处理完时不能启动下一批；
- 写作与审阅可以选择不同 Provider/模型。

### 待建立实施计划

1. `R5 批次领域状态机与编排`
2. `R5 章节生成与 provisional 上下文`
3. `R5 自动审阅与异构模型分工`
4. `R5 检查点、熔断与作者救局`
5. `R5 GenerationAttempt 与非破坏性回退`
6. `R5 逐章定稿与待重建记忆`

## 11. R6：Context Manifest 与长篇连续性

### 目标

将批次闭环升级为可解释、可测量并可扩展到百万字的长期连续性系统。

### 范围

- 建立硬约束、结构、当前状态、摘要和证据五层记忆；
- 实现近场叙事、远场骨架、事实有效区间和过期状态降权；
- Context Manifest 长期保存结构化引用、预算、原因、版本和哈希；
- Invocation Artifact 使用压缩、去重和保留策略；
- 建立可幂等重建的记忆抽取任务；
- 建立固定种子、生成规格和黄金查询的合成长篇 Harness；
- PR 运行 50–100 章缩小集，Nightly/Release 运行 500 章完整集；
- 测量 Recall@10、证据支持率、过期事实误召回、Token、冷/热性能和项目体积。

### 退出标准

- 每次生成可以解释使用了哪些 canonical 来源及原因；
- Context 不超过任务 Token/字符预算；
- 长篇指标达到产品需求 9.2 的门槛；
- 清理完整调用工件后仍能解释 canonical revision 的上下文组成；
- 项目打开和正文编辑不需要加载历史完整 Prompt。

### 待建立实施计划

3. `R6 Invocation Artifact 存储与保留`

## 12. R7：高层设定变更与影响分析

### 目标

让作者可以安全修改高层设定，同时保护历史定稿并获得可解释的影响范围。

### 范围

- `future_only`、`in_story_change` 和 `retcon` 三类意图；
- 扫描历史定稿、确认资产、未定稿候选、路线图、锚点、伏笔和派生记忆；
- 结构化引用优先，必要时才读取原文或调用模型；
- 历史定稿只报告冲突或创建显式修订候选；
- 未定稿内容支持重写、调整路线图、保留例外、废弃或创建分支；
- 影响方案绑定 canonical head、扫描覆盖和预计费用；
- 高影响变更创建一致性快照并建议剧情分支。

### 退出标准

- 三类变更意图产生不同且正确的影响范围；
- 每项历史冲突带章节/revision 证据；
- 相关内容变化后旧影响方案自动失效；
- 执行影响方案不会静默修改历史定稿；
- 失败或取消不破坏原资产和候选。

### 待建立实施计划

1. `R7 ConstraintChangeIntent 与生效边界`
2. `R7 全局影响候选集与证据检索`
3. `R7 影响方案失效与执行`
4. `R7 高影响快照与剧情分支入口`

## 13. R8：整书档案生成与全书聚合

### 目标

在保留现有快速导入和即时正文读写的前提下，建立可恢复的整书档案生成任务；程序内部可以分章、分卷处理，但最终向作者交付一份全书层面的档案候选包。

### 范围

- 快速导入不调用模型，导入完成后正文立即可读、可编辑和手工续写；
- 用户显式启动 `WholeBookArchiveJob`，任务冻结包含章节 revision/hash 的 `SourceManifest`；
- 内部按章节提取、按卷聚合，再执行全书实体解析和全书综合，不把内部切片暴露为用户确认单位；
- 后台任务支持暂停、恢复、取消、优先级调整和仅重试失败步骤，统一使用 R1 JobEvent 与 R6 Context Manifest；
- 全书实体解析处理同名实体、别名、身份合并、时间演变、字段冲突和跨章节多证据；
- 原文在任务期间变化时，将受影响结果标记为 stale，并支持基于 SourceManifest 的增量重算；
- 最终生成版本化 `ArchiveCandidateBundle`，由 R3 的统一审阅和原子确认路径写入正式资产；
- AI 批次续写只使用作者已确认的正式档案；未生成或未确认档案时，作者仍可手工写作。

### 退出标准

- 百万字导入不等待模型处理即可阅读、编辑和手工续写；
- 合成 500 章以上长篇可在内部切片处理，最终结果以整书档案候选包交付而不是逐章结论；
- 后台失败或应用重启不会丢失已完成步骤，能够从持久化状态恢复；
- 原文变更会使相关结果失效，不会把过期结果表现为已完整理解；
- 整书候选保留跨章节证据、冲突和覆盖状态，并遵循 R3 的原子正式资产写入规则。

### 待建立实施计划

1. `R8 WholeBookArchiveJob 与来源快照`
2. `R8 分段抽取与分卷聚合`
3. `R8 全书实体解析与综合`
4. `R8 整书候选审阅与增量重算`

## 16. 阶段过关规则

每个阶段的最后一个实施计划必须执行阶段验收，至少包括：

1. 对照本路线图逐项检查范围和退出标准；
2. 运行该阶段涉及的全部 Go、前端、迁移、fixture 和构建验证；
3. 检查 Windows/macOS 影响，不适用时记录理由；
4. 更新产品、设计、系统、验收和运维文档中受影响的内容；
5. 检查项目包、日志、测试工件和提交中不存在凭据或真实作者正文；
6. 记录仍未完成但明确属于后续阶段的项目，不能以隐藏缺口的方式宣告完成。

出现以下任一问题时不得进入下一阶段：

- 可能损坏 canonical 正文或确认资产；
- 候选可以绕过作者确认进入正式事实；
- 真实 API/订阅成为 CI 必需条件；
- 项目迁移或恢复缺少失败回滚；
- Model IO 长期阻塞作者正文保存；
- Windows/macOS 关键行为只有一个平台被验证；
- 退出标准只能通过手工修改数据库或删除有效锁实现。

## 17. 实施计划创建顺序

R0、R1 与 R2 已完成，下一阶段从 R3 正式资产写入与整书档案确认开始。一个阶段包含多个独立能力时，按“领域/协议基础 → 持久化/平台适配 → Wails binding → React 交互 → 阶段验收”的依赖拆分计划，但每份计划仍应尽可能形成可运行的纵向结果。

实施计划文件使用：

```text
docs/plans/YYYY-MM-DD-r<阶段>-<能力>-implementation.md
```

计划状态为 `draft/approved/in_progress/completed/superseded`。只有 `approved` 或 `in_progress` 的计划可以指导实现；产品设计变化后，旧计划必须更新或标记 `superseded`，不能继续凭历史任务清单开发。

R0、R1 与 R2 已全部完成。当前进入 R3 正式资产写入与整书档案确认；R3–R10 继续保留阶段边界，待前一阶段退出后再逐项建立文件级计划。
