# R3 智能体内核与创作质量验证

> 状态：实现中（第 1–7 步已完成，下一步为第 8 步“薄界面与人工盲评”）
>
> 所属阶段：R3
>
> 设计目标：建立可版本化、可恢复、可比较、可回归的 Agent Kernel，并用固定原创测试集证明“规划、写作、审阅、修订”相对同模型单次直出具有稳定、可记录的质量提升。

## 1. 结论

R3 是后续作品策划、单章写作、批次创作和长期记忆的共同底座，但它不直接交付完整的创作驾驶舱或正式章节创作页面。

本阶段采用以下主线：

```text
版本化任务协议
→ 能力与模型槽解耦
→ 版本化工作流注册表
→ 运行冻结与可恢复执行
→ 结构化审阅和确定性门禁
→ 有界修订与候选隔离
→ 稳定公开阶段与候选谱系
→ 创作质量 Harness
→ 人工盲评和阶段过关
```

核心判断不是“多 Agent 一定更好”，而是通过同输入、同模型来源、同预算记录的对照实验，证明编排后的修订稿比单次直出更可接受。如果质量没有提升，R3 必须停留在 Harness 中调整 Prompt、Schema、上下文和工作流，不能把不稳定能力接入 R4/R5 正式界面。

R3 首版必须保持以下约束：

- 复用现有 `AgentRun`、Provider、运行冻结、JobEvent、JobSnapshot、ChangeSet 和候选隔离能力，不建立平行运行时；
- 工作流节点数量可变，但执行顺序在一个版本内确定，不允许模型临时发明步骤；
- 自动修订默认最多一次，格式修复最多一次，不允许无上限自循环；
- Prompt、工作流、输出契约和装配器均显式版本化，执行时不得解析 `latest`；
- 规划、写作和审阅相互隔离，审阅模型不读取其他审阅结论，写作模型只在修订节点接收规范化问题清单；
- R3 输出只进入 Harness 结果或未确认候选，不写入 canonical 正文和正式资产；
- 创作质量 Harness 与 R7 长篇连续性 Harness 分离，不能用连续性指标代替正文质量。

## 2. 范围与非目标

### 2.1 本阶段范围

- 统一 Agent 任务信封、节点结果、审阅发现、质量判定和运行溯源契约；
- 将稳定的“能力”与 R2.1 的三个模型配置槽解耦；
- 建立不可变工作流、Prompt、Schema 和装配器注册表；
- 将现有固定三步流水线改造成可执行版本化节点列表的 Agent Kernel；
- 冻结每个节点实际使用的连接、模型、参数、预算、Prompt、Schema、输入摘要和上下文清单；
- 支持结构化作品策划、章节细纲、正文、综合审阅和有边界修订；
- 把现有章节细纲能力收口为可演进的章节导演协议，并用 Harness 比较最小导演、增强导演、专业状态分析和拆分审阅工作流；
- 建立确定性写作 lint、质量门禁、失败分类、取消、重试和恢复；
- 建立固定原创测试集、单次直出基线、智能体初稿、修订稿和人工盲评；
- 提供运行观察、结果对比、审阅问题和人工评分所需的测试入口或薄界面；
- 为 R4/R5 提供稳定的作者可见运行阶段、可恢复运行投影、候选谱系和作者定向修订输入契约；
- 使用 Fake/Recorded Provider 做 CI，使用作者明确选择的真实模型做本地质量验证。

### 2.2 明确不在 R3 实现

- R4 的三套故事方向正式页面、作品方案确认和正式资产写入；
- R5 的章节定稿事务、记忆提取和完整正文审阅工作台；
- R6 的多章批次、检查点、回退和 provisional 跨章上下文；
- R7 的全文检索、五层长期记忆和 500 章连续性 Harness；
- 在线 Prompt 市场、作者模板市场、自动扫榜、第三方小说抓取；
- 自动替换 canonical 正文或跳过作者确认；
- R4/R5 的作品级对话会话、待确认 `AssistantAction`、字段/选区写回命令和正式资产影响分析；
- 用单一 AI 检测器判断“AI 味”或宣称可发布保证。

## 3. 现有基础与必须解决的缺口

### 3.1 可复用基础

当前代码已经具备：

- OpenAI/Anthropic 统一 Provider 端口；
- 应用级连接、三角色方案和项目锁定的精确版本；
- 每个运行步骤的 Provider、模型、参数和预算冻结；
- `AgentRun` 的排队、运行、完成、失败、取消、恢复和重试；
- 不持有工作区全局锁的模型调用；
- 持久化 `JobEvent`、`JobSnapshot` 和 cursor 补拉；
- Context、Plan、Draft、Review 工件和 ChangeSet 候选；
- 真实调用前来源与预算确认、调用后 Token 用量展示。

### 3.2 当前缺口

- `AgentRun` 强制固定为 `planner → writer → continuity_reviewer` 三步，能力和模型配置槽耦合；
- Prompt、Schema 和工作流主要是代码常量，没有独立版本、哈希和兼容策略；
- 结构化输出只验证“能解析”，缺少按任务类型的强领域校验；
- 运行只保存大粒度 Context 工件，不能精确解释每个节点使用了哪些输入及其版本；
- 审阅结果缺少统一类别、严重度、正文范围、约束证据和处理状态；
- 当前流水线没有独立内容审阅、文风 lint、质量门禁和有界修订；
- 没有同输入的单次直出对照、盲评、接受率和退化检测；
- 没有明确区分“工作流执行成功”和“作品质量通过”。
- `JobSnapshot` 仍主要暴露内部 step ID，缺少与工作流节点拓扑解耦的作者可见阶段和候选就绪状态；
- 当前 `revise_draft`/`revise_blueprint` 只覆盖质量问题驱动的自动修订，尚未形成可供 R4/R5 安全复用的“作者指定目标、保持项和基线候选”输入契约；
- Artifact 可以通过输入引用追踪来源，但缺少直接供候选比较、撤销和恢复使用的版本谱系关系。

R3 必须解决这些缺口，但不能重写已经验证的 Provider、作业可靠性和候选系统。

## 4. 不可破坏的领域规则

1. `AgentRun` 的终态表示工作流是否执行完成，不等同于作品质量合格。
2. 质量结果单独使用 `passed`、`needs_review`、`blocked`；即使工作流执行完成，也可以因硬约束失败而 `blocked`。
3. 模型输出永远不是 canonical；R3 只能写 Harness 工件或未确认候选。
4. 运行创建时冻结所有可变依赖；执行和恢复阶段只读冻结值。
5. 重试创建新 attempt，旧节点输出、问题、用量和费用记录保留。
6. 格式修复和语义修订是不同节点，分别计费、留痕和受预算控制。
7. 确定性门禁失败不得通过改写分数或删除问题隐藏。
8. 审阅节点只接收原始任务约束、冻结上下文和待审文本；独立审阅之间互不读取结论。
9. 修订节点只接收可展示的规范化发现，不接收其他模型隐藏推理。
10. 任何 Provider 回退、模型切换或增加付费调用都必须重新获得授权，R3 内核不得自动换源。
11. 质量问题驱动的自动修订与作者定向修订使用不同的 `revision_mode`；作者指令不能伪造成 `ReviewFinding`，自动修订也不能借作者指令扩大修改范围。
12. R3 只负责生成可审阅的新候选及其谱系，不执行 R4/R5 的对话 Action，也不把候选应用到正式资产或 canonical 正文。
13. 产品界面只依赖版本化公开阶段和运行投影；内部节点拆分、合并或更名不能改变同一公开阶段的产品语义。

## 5. 核心架构

```text
Harness/薄界面
    ↓ 创建任务
Agent Application Service
    ↓ 冻结
Workflow Registry ─ Prompt Registry ─ Schema Registry
    ↓ 编译节点
Agent Kernel / Orchestrator
    ├─ Context Assembler
    ├─ Capability Resolver
    ├─ Provider Runtime
    ├─ Structured Output Validator
    ├─ Deterministic Quality Gates
    ├─ Finding Merger
    ├─ Public Stage Projector
    └─ Candidate / Artifact Writer
    ↓
AgentRun + Steps + Artifacts + Findings + ContextManifest
    ↓
JobEvent / JobSnapshot / Thin UI
```

模块边界：

- `internal/domain/agent`：任务、能力、工作流、发现、质量状态和状态转换；
- `internal/application/agentkernel`：工作流编译、节点执行、预算、取消、恢复和质量判定；
- `internal/application/ports`：Provider、注册表、上下文装配、工件、Harness 结果等端口；
- `internal/persistence/sqlite`：项目内运行、Manifest、问题和候选持久化；
- `internal/agentassets`：内置 Prompt、Schema、工作流定义和哈希注册；
- `internal/quality`：确定性 lint、评分聚合和 Harness 应用服务；
- `apps/desktop`：薄 Wails DTO 和事件通知；
- React：运行观察、A/B/C 对比、问题查看和人工评分，只消费公开阶段和权威投影，不实现工作流规则或解释内部节点 ID。

现有 `workspace.Service` 继续负责活动项目生命周期和项目锁；具体工作流执行逐步委托给 `agentkernel.Service`，避免继续扩大单个 `agent.go`。

## 6. 统一任务协议

### 6.1 稳定任务类型

首版任务类型：

| 标识 | 作用 | 主要输出 |
|---|---|---|
| `story_blueprint` | 从原创创意形成可评测作品策划 | 作品定位、冲突、人物弧、世界规则、结构 |
| `chapter_plan` | 将章节目标转成可执行场景节拍 | 场景、目标、冲突、信息释放、钩子 |
| `chapter_draft` | 根据细纲生成正文初稿 | 标题、正文、完成说明 |
| `review_bundle` | 独立检查连续性、内容和文风 | 结构化发现列表与质量摘要 |
| `revise_draft` | 根据规范化发现进行有边界修订 | 修订正文和逐项处理结果 |
| `revise_blueprint` | 根据规范化发现修订作品方案 | 结构化作品方案、逐项处理结果和变更证据 |
| `baseline_draft` | 同输入单次直出对照 | 未经过多步骤编排的正文 |

任务类型是外部稳定契约；内部工作流可以组合多个能力节点完成一个任务。

`revise_draft` 和 `revise_blueprint` 同时允许质量修订与作者定向修订，但必须通过版本化 `RevisionDirective` 区分来源：

```text
revision_mode: quality_findings | author_directed
base_artifact_id / base_digest
target_refs[] / preserve_refs[]
finding_ids[]（quality_findings 必填）
author_instruction_ref（author_directed 必填）
```

- `quality_findings` 继续只处理规范化问题清单；
- `author_directed` 只处理作者明确指定的目标，非目标字段和段落必须保持；
- `base_digest`、目标引用和保持项在运行创建时冻结，恢复和应用前都可用于检测过期；
- R3 Harness 只验证该契约能够产生独立候选。R4/R5 负责把对话建议转成待确认 Action、授权费用、构造 Directive，并决定是否应用候选。

### 6.2 `AgentTaskEnvelope`

每个节点接收不可变任务信封：

```text
task_id / run_id / step_id / attempt
task_kind / capability
workflow_id / workflow_version
project_id / branch_id / canonical_head
author_instruction_ref
input_artifact_refs + input_digest
constraint_refs
context_manifest_id
execution_binding
prompt_binding
schema_binding
budget
deadline / cancellation_token
```

关键字段：

- `execution_binding`：配置槽、连接 ID、Provider、模型、参数和凭据引用；
- `prompt_binding`：Prompt ID、版本和 SHA-256；
- `schema_binding`：Schema ID、版本和 SHA-256；
- `budget`：节点最大输出、运行剩余 Token、字符预算、格式修复预留和修订预留；
- `input_digest`：按固定顺序计算的输入引用与内容哈希，恢复时用于检测错配；
- `canonical_head`：Harness 可为空；项目任务必须记录创建时的正式内容头。
- 修订任务的 `input_artifact_refs` 必须包含 `RevisionDirective` 与基线候选；`input_digest` 覆盖 Directive、基线内容、目标和保持项，不能只对作者自然语言计算哈希。

信封不包含 API Key。密钥只在节点执行时凭冻结的凭据引用从操作系统凭据库读取。

### 6.3 `AgentTaskResult`

```text
task_id / run_id / step_id / attempt
status
structured_output_artifact_id
primary_content_artifact_id
finding_ids
quality_status
input_tokens / output_tokens / provider_request_id
started_at / completed_at
output_digest
```

模型自由文本不能直接决定状态。应用层必须按任务类型解码到强类型 Go 结构，执行领域校验后才可生成结果。

### 6.4 结构化输出策略

- JSON Schema 用于约束 Provider 输出，Go 类型与 `Validate()` 是本地最终校验；
- 解码必须拒绝未知关键字段、缺失必填字段、非法枚举、空正文和越界列表；
- 正文放在结构化信封的 `body` 字段，解析后以独立正文工件保存；
- Provider 不支持原生结构化输出时，仍发送明确 Schema，并执行相同本地校验；
- 仅格式不合法时允许一次 `format_repair`，使用原节点模型、冻结 Schema 和独立预算；
- 格式修复不得增加新事实或改变正文语义；修复前后均保存哈希；
- 修复仍失败则节点失败，不能使用正则猜测领域数据。

## 7. 能力与模型槽解耦

### 7.1 稳定能力标识

| 能力 | 职责 | R2.1 默认模型槽 |
|---|---|---|
| `story_architect` | 题材定位、冲突、人物弧和结构 | `planner` |
| `chapter_planner` | 章节导演：把路线图与冻结上下文转成可执行叙事任务 | `planner` |
| `prose_writer` | 叙事正文初稿 | `writer` |
| `continuity_review` | 事实、状态、知识边界、时间线和伏笔 | `continuity_reviewer` |
| `content_review` | 因果、动机、冲突、节奏、钩子和信息密度 | `continuity_reviewer` |
| `style_review` | 重复、套话、机械句式、总结腔和声音同质化 | `continuity_reviewer` |
| `bounded_revision` | 依据公开问题清单修改未确认候选 | 正文默认 `writer`；作品方案显式使用 `planner` |

R3 不增加普通用户必须配置的新槽位。`CapabilityResolver` 先把能力映射到三个兼容槽，再解析项目锁定的创作方案。以后创作方案支持更多能力绑定时，只扩展解析规则，不修改工作流和任务类型。

工作流节点必须同时冻结：

- `capability`：节点为什么存在；
- `role_slot`：本次从哪个配置槽取得模型；
- 实际 Provider、模型和生成参数。

UI 可以显示中文职责和实际模型，不向普通用户暴露内部槽位映射。

### 7.2 独立审阅

R3 标准章节工作流使用一个综合审阅调用输出三类发现，但 Schema 明确区分类别。重要任务可以将三类能力编译为多个独立节点；独立节点只读同一份正文和约束，不读取彼此结果。

正文写作与审阅继续遵守 R2.1 的独立模型约束。后续增加多个审阅槽时，不改变 `Finding` 契约。

拆分审阅工作流必须经过确定性 `FindingMerger` 后才能进入修订。Merger 只执行规范化、稳定排序、精确重复合并、证据关联和结论冲突标记；不得调用模型补写新问题，不得静默降低严重度，也不得把“多个审阅者同意”当成覆盖 canonical 证据的投票。R3 首先保证输入隔离和结果确定性；是否并行执行是调度优化，只有并发、预算、取消和恢复测试通过后才能启用。

### 7.3 章节导演与专业状态分析变体

现有 `chapter_plan` 任务类型和 `chapter_planner` 能力标识保持稳定，但其产品语义统一为“章节导演”。已发布 v1 不原地修改；增强协议发布新的 Prompt/Schema/工作流版本，至少输出：

```text
chapter_goal
scenes[]: pov / desire / obstacle / conflict / information_release / state_change
required_anchors[] / forbidden_reveals[]
ending_hook / improvisation_bounds
canonical_source_refs[] / creative_suggestions[]
```

`canonical_source_refs` 只能引用冻结 Context Manifest 中的来源；`creative_suggestions` 明确表示尚未成为事实的本章建议。Writer 只接收导演任务、专业约束和冻结上下文，不重新自由规划全书。

Harness 可以增加连续性、人物动机与知识边界、伏笔与叙事债务、世界规则等专业状态分析节点。它们统一输出短小的 `ConstraintNote`/风险列表和来源引用，不生成可拼接正文。默认仍由单一主写模型完成整章；多写手整章方案不进入 R3 默认实现，除非后续独立实验在特定题材上证明质量收益足以覆盖声音、衔接和成本风险。

## 8. 版本化注册表

### 8.1 工作流注册表

`WorkflowDefinition` 至少包含：

```text
workflow_id
version
supported_task_kind
nodes[]
edges[]
entry_node
result_node
max_revision_attempts
budget_policy_version
quality_policy_version
definition_hash
```

`WorkflowNode` 包含：

```text
node_id
public_stage_id
capability
role_slot
prompt_id + prompt_version
schema_id + schema_version
input_selectors
output_kind
max_output_tokens
temperature_override（可选）
failure_policy
condition（只允许预定义确定性条件）
```

首版执行器支持确定性顺序和预定义条件分支，不实现模型自由规划 DAG。定义加载后必须校验节点 ID、拓扑、输入来源、结果节点、预算和版本引用；非法定义在启动时失败，不进入运行。

预定义条件不满足时不得调用 Provider。该节点以零用量的完成记录持久化，并生成明确标记 `condition_not_met` 的轻量质量工件，保证事件投影和恢复调度不遗留含义不明的排队节点。

工作流定义一经用于运行不可原地修改。任何节点、Prompt、Schema、预算策略或条件变化都发布新版本。

`public_stage_id` 使用独立的稳定枚举，例如 `context_preparing`、`chapter_directing`、`prose_writing`、`independent_review`、`bounded_revision` 和 `candidate_ready`。多个内部节点可以映射到同一公开阶段；注册表在启动时校验映射，运行快照保存当前公开阶段，不能要求 React 根据 `node_id` 猜测作者文案和进度。

### 8.2 Prompt 注册表

每个 Prompt 由以下部分组成：

- 稳定 ID 和整数版本；
- 角色职责与禁止越权；
- 任务目标；
- 输入区块及顺序；
- 输出契约说明；
- 质量检查清单；
- 内容边界和原创约束；
- SHA-256。

Prompt 作为嵌入式只读资源随应用发布。渲染器只接受声明过的变量，缺少变量或出现未消费变量时失败。Prompt 文本变化必须提升版本并通过 Harness，不允许只改字符串后沿用旧版本。

### 8.3 Schema 注册表

Schema 与 Go 输出类型一一对应并版本化。契约测试必须验证：

- 合法 fixture 可通过 Provider Schema 和 Go 领域校验；
- 缺字段、未知枚举、空正文、重复 ID、非法引用和超限列表被拒绝；
- Prompt 声明的 Schema 与节点引用一致；
- Schema 哈希与运行冻结记录一致。

## 9. 首版工作流

### 9.1 单次直出基线 `baseline.chapter.v1`

```text
相同章节任务与冻结上下文
→ prose_writer 单次生成
→ 确定性 lint
→ 保存基线结果
```

基线必须与标准工作流使用相同写作模型、章节目标、上下文来源和正文最大输出；不能故意使用较差 Prompt 制造优势。基线不读取标准工作流的细纲、审阅或修订结果。

### 9.2 标准章节质量工作流 `quality.chapter.v1`

```text
chapter_planner
→ prose_writer
→ review_bundle（独立审阅模型）
→ deterministic_lint（本地）
→ quality_gate
   ├─ 通过：输出初稿作为最终候选
   └─ 有可修问题：bounded_revision（最多一次）
                    → deterministic_lint
                    → final_quality_gate
```

规则：

- `chapter_planner` 输出场景目标、冲突、转折、信息释放、人物状态变化和结尾钩子；
- `prose_writer` 只读任务、上下文和细纲，不读取审阅标准的预期答案；
- `review_bundle` 不读取 writer 的隐藏推理，只读取正文和显式约束；
- `bounded_revision` 必须逐项返回 `resolved / retained / cannot_resolve`，不得无关重写；
- 每个 `resolved` 问题必须返回 `original_text / revised_text` 变更证据；本地校验将证据依次应用到原候选，结果必须与修订候选完全一致；
- 已通过硬锚点的段落默认保持，除非问题证据指向该范围；
- 第二次门禁后仍有 blocker 时，工作流执行完成但质量状态为 `blocked`；
- 预算不足以保留修订节点时，启动前拒绝标准工作流，不得运行到一半静默省略修订。

### 9.3 作品策划验证工作流 `quality.blueprint.v1`

```text
story_architect
→ review_bundle（逻辑、差异化、可连载性、原创风险）
→ quality_gate
→ bounded_revision（使用 planner 槽，最多一次）
→ final_quality_gate
```

R3 只将结果保存为 Harness 工件。R4 接入时才把同一任务协议映射为可审阅作品方案候选和正式资产。

作品方案修订使用独立的 `revise_blueprint.v1` 结构化结果，不能借用正文 `body` 承载方案。`bounded_revision` 的默认槽仍为 `writer`，但该工作流节点明确冻结为 `planner`，两种绑定都由任务协议校验。

现有 `quality.chapter.v1` 和 `quality.blueprint.v1` 的有界修订保持 `quality_findings` 模式。作者定向修订首版通过专用入口工作流或明确版本升级接入，不能在不提升 Prompt、Schema 与工作流版本的情况下改变现有 v1 语义。

### 9.4 长篇章节工作流实验

R3 Harness 保留 `quality.chapter.v1` 作为最小质量基线，并允许注册下列实验变体：

```text
增强章节导演
→ 主写 Writer
→ 综合审阅
→ lint / gate / bounded revision

增强章节导演
→ 专业状态分析（一个或多个短结构节点）
→ 主写 Writer
→ 拆分独立审阅 + deterministic FindingMerger
→ lint / gate / bounded revision
```

变体必须使用相同 case、正文目标、写作模型来源和可比较预算记录。报告分别展示导演协议命中率、正文质量、事实错误、修订率、失败率、延迟、调用数和 Token 成本。增加专业节点或拆分审阅只有在相关分项指标稳定提升且成本可接受时才进入 R5 默认 `chapter.production`；否则保留为实验版本或特定题材高级工作流。

R3 不实现 `GenerationBatch`、完整长期记忆检索或 `chapter.posthoc`。它只证明同一 Kernel 能冻结和执行这些局部节点契约，后续 R6/R7 通过新的版本化工作流组合复用，不复制运行时。

## 10. 上下文与最小 Context Manifest

R3 不建设完整长期记忆检索，但必须建立后续可扩展的 Manifest 骨架。

每个模型节点生成独立 `ContextManifest`：

```text
manifest_id / version
run_id / step_id
canonical_head
assembler_id / assembler_version
items[]
character_budget / estimated_token_budget
used_chars / truncation
assembled_content_hash
created_at
```

每个 `item` 记录：

```text
source_kind
source_id
source_version
range（可选）
content_hash
order
priority
selection_reason
provisional
included / omission_reason
```

R3 支持的来源限于：固定 Harness 规格、作者指令、当前章节 revision、已有明确选择的结构化资产、上游节点工件和锚点。不得把全部项目资产或整本正文无界装入上下文。

装配顺序固定：

1. 硬约束和禁止项；
2. 当前任务与作者指令；
3. 已确认结构化输入；
4. 当前章节或必要近期正文；
5. 上游节点结果；
6. 软目标和表达偏好。

预算不足时按明确优先级截断，硬约束不得截断；无法容纳硬约束时任务创建失败。

## 11. 审阅发现与确定性质量门禁

### 11.1 `ReviewFinding`

```text
finding_id
run_id / step_id / attempt
category
severity
scope_start / scope_end
quoted_evidence
constraint_ref（可选）
message
suggested_action
status
source
```

枚举：

- `category`：`anchor`、`continuity`、`knowledge_boundary`、`causality`、`motivation`、`pacing`、`hook`、`information_density`、`world_rule`、`foreshadowing`、`repetition`、`style`、`format`、`originality_risk`；
- `severity`：`blocker`、`major`、`minor`、`note`；
- `status`：`open`、`resolved`、`retained`、`cannot_resolve`；
- `source`：`model_review`、`deterministic_lint`、`author`。

正文范围使用解析后正文的 Unicode rune offset，不使用字节 offset。没有直接正文范围的问题必须引用约束或结构字段，不能伪造引文。

### 11.2 确定性 lint

R3 首版至少检查：

- JSON/结构字段完整性；
- 正文为空、目标字数偏差和异常短段落比例；
- Markdown 代码围栏、模型自述、提示词泄漏和“以下是正文”等元话语；
- 硬锚点、禁止词和必须出现实体的确定性匹配；
- 连续重复句、重复段、异常高频短语和连续相同句式开头；
- 机械排比、总结腔、空泛转折词等可解释规则命中；
- 章节标题或正文包含测试集保留专名；
- 修订稿丢失初稿已满足的硬约束。

Lint 只报告可解释命中，不输出“AI 概率”。规则具有 ID、版本、严重度和测试 fixture；阈值变化必须提升质量策略版本。

质量策略 v1 的正文规则固定为：

- 目标长度允许区间为目标 rune 数的 `70%–130%`，超出记为 `major`；未提供目标长度时不猜测；
- 短段落定义为不超过 8 rune；至少 4 段且短段比例达到 60% 时记为 `major`；
- 连续重复句、重复段、至少 3 个句子共享同一 4-rune 短语、连续 3 句使用相同 2-rune 开头记为 `major`；
- 连续 3 句使用“不是……而是……”记为机械排比 `major`；总结腔短语记为 `minor`；
- Markdown 代码围栏、缺失硬锚点、命中禁止项或测试集保留专名记为 `blocker`；模型自述和提示词元话语记为 `major`；
- 所有正文范围使用 Unicode rune offset；LF 与 Windows CRLF 段落边界产生相同规则结果；
- 单规则和单报告具有有界发现数量；发生截断时审阅视为不完整，质量不得为 `passed`。

动态检查输入以 `QualitySpec` 冻结进任务输入，包含目标 rune 数、硬锚点、禁止项和测试集保留专名。章节任务的必要 `ManifestAnchor` 自动并入硬锚点；作品方案不自动继承章节正文锚点。

### 11.3 质量判定

- 任一未解决硬锚点、禁止项、Schema 或安全边界 blocker：`blocked`；
- 无 blocker 但存在 major、预算不足以修订或审阅不完整：`needs_review`；
- 所有 blocker/major 已解决且自动门禁通过：`passed`；
- 模型给出的数值评分只能用于报告，不能覆盖确定性 blocker。

初稿 lint 发现会合并到修订节点可见的公开 `review_bundle`，不进入模型隐藏推理。`minor / note` 保留在报告中但不单独触发自动修订；`major / blocker` 触发一次已冻结的有界修订。最终门禁重新运行 lint，并将修订的 `resolved / retained / cannot_resolve` 与初始问题逐项对账：已解决的初始问题不继续污染最终状态，新引入或仍未解决的问题保持有效。最终修订门禁是运行质量状态的权威结果，但不能覆盖执行失败。

## 12. 运行冻结、预算和恢复

### 12.1 创建阶段

创建运行必须一次性完成：

1. 解析明确工作流 ID 和版本；
2. 校验任务输入和 canonical head；
3. 编译确定性节点列表；
4. 按能力解析模型槽和项目锁定方案；
5. 冻结每个节点的 Provider、模型、参数、Prompt、Schema 和装配器；
6. 为格式修复、审阅和一次修订预留预算；
7. 保存运行、节点、初始 Manifest 引用和 `job_queued`；
8. 返回运行前预览，作者确认后执行。

冻结失败不产生半个可执行运行。数据库写入使用短事务，模型 IO 不在事务内。

### 12.2 预算策略

- 总预算是硬上限，按节点分配并保留应急额度；
- 节点开始前检查剩余额度，不能依靠 Provider 超额后再报错；
- 格式修复、条件复审和修订均计入总预算；
- 标准章节工作流默认最多四次模型调用；只有出现 blocker/major 且已预留预算时才允许一次条件复审；
- Harness 报告基线与工作流的输入/输出 Token、调用次数、耗时和相对成本；
- 任何自动新增调用都必须来自冻结的工作流条件，不能在运行时临时决定换模型或扩预算。

### 12.3 取消、失败和恢复

- 节点开始、完成、失败和质量判定均写 JobEvent；
- 大文本只写 Artifact，事件只存摘要和引用；
- 应用重启后，已完成且输入摘要匹配的节点不重复计费；
- 正在调用时中断的节点进入 `recoverable`，恢复时创建新 attempt，不假设 Provider 请求未计费；
- 新 attempt 使用新的 step ID，旧 attempt、工件、Manifest、问题和用量保持不可变；调度器只选择同一节点的最新 attempt 继续执行；
- 恢复前重新检查项目 generation、canonical head 和输入摘要；项目内容变化时旧运行标记 stale，必须显式重建任务；
- 取消保留所有已产生输出、问题和用量，不创建候选；
- Provider 错误保持稳定分类，不把正文、Prompt 或原始响应写入用户可见错误。

## 13. 持久化设计

### 13.1 演进现有项目数据库

不新增平行 AgentRun 表。通过版本化迁移扩展现有表：

`agent_runs` 新增：

- `task_kind`；
- `workflow_id`、`workflow_version`、`workflow_hash`；
- `canonical_head`、`input_digest`；
- `quality_status`；
- `budget_policy_version`、`quality_policy_version`；
- `max_revision_attempts`。

`agent_run_steps` 新增：

- `node_id`、`capability`、`attempt`；
- `prompt_id`、`prompt_version`、`prompt_hash`；
- `schema_id`、`schema_version`、`schema_hash`；
- `assembler_id`、`assembler_version`；
- `input_digest`、`output_digest`；
- `primary_artifact_id`、`quality_status`。

`role` 保留为实际模型配置槽，数据库约束仍只允许 R2.1 的三个槽；`capability` 表达节点职责。

`agent_artifacts.kind` 扩展为：

- `context`、`task_input`、`plan`、`draft`、`review`、`revision`、`structured_output`、`lint_report`、`quality_report`、`format_repair`。

新增版本化 Artifact 谱系关系，至少表达：

```text
artifact_id / relation / related_artifact_id
base_digest / created_at
```

`relation` 首版包含 `derived_from`、`revises` 和 `supersedes`。谱系只说明候选之间的来源，不代表候选已经写入 canonical；删除或重试运行不得让现有候选失去基线引用。

新增：

- `context_manifests`；
- `context_manifest_items`；
- `agent_review_findings`；
- 必要的 run/step/category/status 索引。

步骤正文完整内容以 Artifact 为准。`agent_run_steps.output` 暂时保留兼容展示，但新运行只保存有界预览，避免同一大文本无限重复。

### 13.2 Harness 结果隔离

固定测试定义进入仓库，真实模型输出、评分和报告不得进入 Git。

本地 Harness 使用应用数据目录中的独立 `harness.db` 保存：

- `harness_runs`：数据集、工作流、方案版本、随机化种子和状态；
- `harness_case_results`：case、baseline/initial/revised 工件、用量、门禁和匿名展示顺序；
- `harness_ratings`：盲评维度、接受决定、备注和评分者本地标识；
- `harness_reports`：聚合指标和版本对比。

`harness.db` 不保存 API Key。删除 Harness 数据不影响任何小说项目；项目恢复也不依赖 Harness 数据。

## 14. 创作质量 Harness

### 14.1 固定原创数据集

数据集使用版本化 JSON/YAML fixture，首版不少于 12 个原创 case：

- 4 个作品策划 case：东方幻想、都市悬疑、现实情感、轻科幻；
- 8 个章节 case：开篇钩子、人物对话冲突、动作场景、情绪转折、线索揭示、世界规则展示、过渡章节、连续性约束。

每个 case 包含：

```text
case_id / dataset_version / genre / task_kind
original_seed
story_spec
confirmed_constraints
chapter_goal
character_voices
required_anchors / soft_anchors / forbidden_items
target_length
automatic_expectations
rating_dimensions
```

所有 case 必须原创、可审计，不包含真实小说正文、受保护角色、专名或情节链。修改 case 必须提升数据集版本，历史报告继续引用旧版本。

### 14.2 对照组

每个章节 case 至少产生：

- A：同模型单次直出；
- B：标准工作流初稿；
- C：审阅后的有界修订稿。

展示时使用由固定随机种子生成的匿名顺序，不显示 A/B/C 的真实身份、模型或工作流。评分提交后才揭示来源，避免确认偏差。

### 14.3 自动报告

按 case、题材、任务和版本分别报告：

- Schema、长度、锚点、禁止项、格式和重复门禁；
- blocker/major/minor 数量及修订解决率；
- Provider、模型、Prompt、Schema、工作流和装配器版本；
- 输入/输出 Token、调用次数、耗时和失败重试；
- baseline、initial、revised 的差异；
- 不同工作流变体的导演协议命中、专业约束采用、审阅独立性、Finding 合并冲突、延迟和边际 Token 成本；
- 退化 case 列表，不能只给总平均分。

### 14.4 人工盲评

章节维度采用 1–5 分：

- 开篇钩子/阅读驱动力；
- 情节推进和有效信息密度；
- 人物动机；
- 人物声音区分；
- 场景化表达；
- 因果与冲突；
- 情绪递进；
- 语言自然度和可读性；
- 明显模板感/AI 痕迹（反向计分）；
- 原创风险。

策划维度采用 1–5 分：

- 核心卖点；
- 三层冲突和可持续升级；
- 主角欲望、缺陷和代价；
- 世界规则对剧情的驱动；
- 人物弧与主线耦合；
- 连载扩展性和阶段回报；
- 逻辑完整性；
- 差异化与原创风险。

每个结果还必须选择：`可直接接受`、`少量修改`、`大量修改`、`整章/整案重写`。

## 15. R3 质量过关门槛

R3 使用一套明确的参考创作方案完成本地真实模型验证。门槛不是对所有模型的质量承诺，而是证明内核和工作流至少在一个可复现配置上有效。

### 15.1 基础设施门槛

- 固定 case 的运行、取消、失败、恢复和重试均可复现；
- 100% 运行可追踪到冻结模型、Prompt、Schema、工作流、输入摘要和用量；
- 100% 非法结构化输出被拒绝或经一次格式修复后通过，不存在正则猜测入库；
- 100% hard anchor、禁止项和 Schema blocker 不会被模型评分覆盖；
- 任何路径均不修改 canonical 正文或正式资产；
- Fake/Recorded Provider 自动测试和双平台生产构建通过。

### 15.2 初始质量门槛

在不少于 12 个固定 case、每个 case 至少完成两轮匿名比较且累计不少于 30 组有效配对判断时：

- 修订稿相对单次直出胜率不低于 60%，负率不高于 20%；
- 修订稿相对智能体初稿胜率不低于 55%，且不能以明显增加事实错误换取文风分数；
- `可直接接受 + 少量修改` 不低于 70%；
- `整章/整案重写` 不高于 15%；
- 章节关键维度中位数均不低于 3.5/5，策划关键维度中位数均不低于 3.5/5；
- hard anchor 和禁止项通过率 100%；
- 不允许任一题材连续两轮在人物动机、因果、可读性或原创风险上低于 3/5；
- 标准章节工作流总模型调用默认不超过 4 次；条件复审触发率和额外成本必须单独报告。

样本不足时只显示趋势，不宣称过关。自动模型评分可以作为辅助观察，但不计入上述人工门槛。

### 15.3 退化规则

以下任一发生即判定新版本退化，不能替换当前参考版本：

- 新增 hard anchor 或禁止项失败；
- 任一关键维度下降超过 0.5 分且没有成本/成功率方面的明确收益；
- 接受率下降超过 10 个百分点；
- 整章重写率上升超过 5 个百分点；
- 失败、超时或 Schema 修复率显著上升；
- 平均 Token 成本增加超过 25% 而盲评胜率无显著提升。

增强导演、专业状态分析或拆分审阅相对最小工作流触发上述退化规则时，不得成为 R5 默认工作流；允许保留为实验版本继续校准，但不能以节点更多或流程更复杂替代质量证据。

## 16. 薄界面和桌面 API

R3 只增加“智能体实验室”薄入口，不改变正式作品导航信息架构。

### 16.1 页面

1. **测试集与运行配置**：选择数据集版本、参考创作方案、工作流版本、case 和预算；
2. **运行观察器**：公开阶段、状态、模型来源、Token、耗时、取消、失败和恢复；内部节点只在诊断详情中展示；
3. **结果对比**：匿名并排或逐份阅读 baseline/initial/revised；
4. **审阅与门禁**：按类别、严重度和正文范围显示发现；
5. **人工评分**：维度评分、接受决定、备注和提交后揭示来源；
6. **回归报告**：按题材、case、维度、版本和成本展示提升与退化。

页面必须明确“实验结果不会写入作品正文或正式资产”。真实运行前复用 R2.1 的 Provider、模型、预算和费用确认。

### 16.2 Wails 用例边界

Wails 层只做 DTO 转换和安全错误映射；React 不读取 Prompt 文件、不计算质量状态、不直接调用 Provider 或 SQLite。

## 17. 安全、隐私与原创边界

- 固定 Harness 输入均为仓库内原创 fixture；
- 真实 Provider 只接收作者在运行预览中确认的 case 内容；
- API Key、凭据引用和完整 Provider 请求体不进入 Harness 报告；
- 默认不记录模型隐藏推理；只保存结构化输出、正文、公开问题、版本、哈希和用量；
- 日志和错误不包含完整正文、Prompt、响应或密钥；
- Harness 导出前显示包含的生成文本和元数据范围；
- 不调用网络搜索比对第三方小说，不把相似度或 AI 检测分数当质量真相；
- 内容政策拒绝必须显示为独立错误，保留已有结果，不自动切换 Provider。

### 第 7 步：长篇与上层交互契约收口

状态：已完成。

实现：

- 为 Workflow Node 增加稳定 `public_stage_id`，并生成包含公开阶段、进度、质量状态、可恢复性、费用和候选可用性的运行投影；
- JobEvent 继续携带内部 step 引用用于诊断，普通界面只消费公开阶段；Bridge 重挂载和 snapshot 重建后投影一致；
- 增加版本化 `RevisionDirective`，明确质量修订/作者定向修订、基线候选、目标、保持项和作者指令；
- 增加 Artifact 候选谱系，能从修订候选回到基线、工作流、Manifest 和输入摘要；
- 为作者定向的方案与正文修订增加 Recorded Provider 契约 fixture，但不实现对话会话、Action 确认或 canonical 写回。
- 发布不可变的增强章节导演 Prompt/Schema/工作流版本，区分 canonical 来源、创作建议、禁止提前揭示项和允许即兴范围；
- 增加可选专业状态分析节点的公共短结果契约，以及确定性 `FindingMerger`；注册最小、增强导演和拆分审阅 Harness 变体，不默认启用未经质量证明的多节点方案。

测试：

- 内部节点重命名或多个节点映射到同一公开阶段时，运行观察投影和恢复语义不变；
- 公开阶段只能来自注册表允许值，未知值在工作流加载时失败；
- 作者定向修订只能改变目标引用，保持项和非目标内容不变，基线哈希变化时拒绝重放；
- 质量修订必须有 finding，作者定向修订必须有作者指令，两种模式不能混用；
- 候选谱系在失败、重试、恢复和应用重启后完整，且不暗示 canonical 已更新。
- 章节导演引用只能指向冻结 Manifest；专业状态分析不输出正文；拆分审阅输入彼此隔离，Finding 合并在乱序输入下产生相同结果；
- Harness 报告能按工作流变体比较质量、事实错误、失败率、延迟、调用数和 Token 成本，不能用总体均分掩盖某一题材退化。

实现结果：

- Workflow Node、编译快照和 RunStep 新增注册表校验的稳定 `public_stage_id`；JobSnapshot 持久化公开阶段、步骤进度、质量状态、可恢复性和候选可用性，Bridge 重挂载无需根据内部节点 ID 猜测界面状态；
- JobEvent 保留内部 step/node 诊断引用，同时携带公开阶段；旧三角色运行通过兼容映射获得公开阶段，已完成运行统一投影为 `candidate_ready`；
- 新增版本化 `RevisionDirective`，严格互斥 `quality_findings` 与 `author_directed`，冻结基线候选、摘要、目标、保持项、finding 或作者指令引用；
- 新增作者定向修订候选应用用例和 Prompt/Schema 资源，基线摘要变化、目标外修改、保持项修改或模式混用均被拒绝，只产生独立候选；
- 项目数据库迁移至 v20，新增 `agent_artifact_relations`，支持 `derived_from`、`revises`、`supersedes`；有界修订自动保存候选到基线的 `revises` 谱系与基线摘要；
- 发布不可变章节导演 Prompt/Schema v2，并注册 `quality.chapter.director@1` 与 `quality.chapter.split-review@1`；现有 `quality.chapter@1` 保持最小质量基线；
- 新增带 canonical 来源引用的 `ConstraintNote` 短结果契约和确定性 Finding Merger；Merger 在乱序输入下稳定排序、精确去重并标记同证据冲突，不创建新问题；
- Harness 注册最小、增强导演和拆分审阅三个公平对照变体，实验变体默认禁用；报告候选证据增加导演协议、专业约束采用、审阅独立性和合并冲突指标。

停止条件：R4/R5 可以只通过应用用例构造版本化修订请求、观察稳定公开阶段并取得带谱系的新候选；R5 还能从 Harness 证据中选择已验证的章节导演和审阅组合，无需读取内部节点 ID，也无需修改 Agent Kernel 主协议。

- 现有三角色方案继续有效；能力解析器提供兼容映射；
- 旧 AgentRun 不补造不存在的 Prompt/Schema 哈希，展示为 legacy，并保持可读；
- 新运行必须使用明确工作流版本，不能落回旧常量流水线；
- R4 复用 `story_blueprint` 任务和结果 Schema，增加候选编辑与正式资产映射；
- R5 复用 `quality.chapter.v1`，增加章节候选、作者编辑、定稿和记忆候选；
- R6 在同一内核上增加批次调度、provisional 上下文和检查点，不复制单章工作流；
- R7 扩展 ContextAssembler 和 Manifest 来源，不改变任务信封、节点结果和 Finding 主契约；
- 后续增加内容编辑、文风编辑专属模型绑定时，只扩展创作方案能力映射和 UI，不修改已有运行快照。
- R4/R5 的 `AssistantSession`、`AssistantAction`、费用确认、字段路径白名单、选区范围校验和候选应用命令属于应用层；它们调用 R3 的作者定向修订契约，但不进入 Agent Kernel 调度器。

## 21. R3 完成标准

必须同时满足：

- 版本化任务、工作流、Prompt、Schema、装配器和质量策略均已落地；
- 标准作品策划与章节质量工作流可通过无正式业务页面的入口运行；
- baseline、initial、revised 可公平对照；
- 写作与审阅可使用不同 Provider 或模型；
- 每个结果可追踪到冻结输入、模型、Prompt、Schema、工作流、Manifest 和用量；
- 失败、取消、重试、恢复和应用重启不会修改 canonical 或重复应用节点；
- 上层界面可以通过稳定公开阶段观察运行，并从任一修订候选追踪到基线、输入摘要和 Context Manifest；
- 质量问题修订与作者定向修订具有不同的验证规则，均只产生候选且不会越过目标和保持项；
- 增强章节导演、专业状态分析和拆分审阅均可作为独立工作流版本进入公平 Harness；确定性 Finding Merger 可处理重复与冲突且不创造新问题；
- 确定性门禁和结构化审阅可解释，自动修订有界；
- 固定原创数据集和人工盲评达到第 15 节门槛；
- Fake/Recorded Provider、迁移、并发、Wails 和 React 自动测试通过；
- macOS、Windows 生产构建与人工验收通过；
- 未达到门槛的题材或能力被明确记录，不提前接入对应完整上层页面。

满足上述标准后，R4 才开始把已经验证的作品策划能力接入三套方向、作品方案、世界观、大纲和正式资产闭环；R5 再接入已验证的单章写作能力。
