# 织境 Story Studio 实施计划规范

本目录保存与[总体开发路线图](../roadmap/development-roadmap.md)绑定的具体能力实施计划。实施计划是阶段执行工具，不是产品需求或架构决策；发生冲突时必须回到产品需求、交互设计、系统技术设计和 ADR 修正规划。

## 一份计划的范围

一份计划只解决一个边界清晰、可独立验证的能力，例如：

- Agent job lease 与工作区锁隔离；
- JobEvent 持久化与应用 API；
- 作品方案正式资产映射；
- 批次检查点与作者救局；
- 长篇 Harness 生成器。

不得用一份计划同时覆盖完整 R0–R10，也不得以“后续补充”“类似实现”省略关键步骤。

## 文件命名

```text
YYYY-MM-DD-r<阶段>-<能力>-implementation.md
```

例如：

```text
2026-08-06-r0-ci-test-baseline-implementation.md
```

## 必备内容

每份计划至少包含：

1. 状态：`draft/approved/in_progress/completed/superseded`；
2. 所属路线图阶段；
3. 对应产品需求、交互设计、系统设计和 ADR；
4. 目标、范围与明确不包含内容；
5. 当前代码基线和已知缺口；
6. 文件级改动范围与模块职责；
7. 数据模型、迁移、兼容和恢复策略；
8. 按 TDD 顺序拆分的实现步骤；
9. fake/fixture、错误、取消、幂等和并发测试；
10. Windows/macOS 影响；
11. 精确验证命令和预期结果；
12. 文档更新、阶段退出证据和回滚方式。

## 执行规则

- 计划批准前不开始对应大型功能代码；
- 大型计划在隔离 worktree 中执行；
- 每个实现步骤先写失败测试，再写最小实现；
- Wails binding 保持薄，React 不直连 SQLite、文件系统或 Provider；
- 不在计划中引入未获批准的 Rust、CGO/FFI、Wails v3 或云端必需服务；
- 计划完成后先运行全部验证，再更新状态；
- 产品设计变化时，正在执行的计划必须重新核对；不能用旧计划覆盖新需求。

## 完成与保留

计划完成后保留为执行记录，标记完成提交和验证证据。若实现方向被新设计取代，计划标记为 `superseded` 并链接替代计划；不得删除仍用于解释数据库迁移、恢复或兼容决策的实施记录。
